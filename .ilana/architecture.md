# MailX Architecture, Invariants, Security, Limitations (current through v0.26)

Verified against HEAD `481da4a` on 2026-09-21. This file states CURRENT truth. Superseded designs are kept only
under "Superseded" so they are never read as current. History lives in `milestones.md`; rationale IDs in `decisions.md`.
Update this file whenever a task changes anything listed here (see `CLAUDE.md`).

## Purpose

MailX: open-source, developer-first email infrastructure written from the protocol up in Go (module `github.com/Ferousco-dev/mailx`,
Go 1.27.1; deps: pgx/v5, go-redis/v9, x/net). It began as a Go-learning project and grew into an owned SMTP/delivery/API stack.

## Runtime shape

One binary `cmd/mailx`.
- No args + no `DATABASE_URL`: `serve()` = SMTP receiver + FileStore only (original v0.1-v0.14 behavior).
- No args + `DATABASE_URL`: `runFull()` runs components under one shutdown signal: `smtp`, `dispatch`, `worker`,
  `webhook-fanout`, `webhook-worker`, `api`, `idempotency-cleanup`. **Any component failing or exiting stops the whole process** (`runComponents`).
- Subcommands: `list`, `inspect <id>`, `migrate`, `create-tenant`, `create-api-key`, `rotate-api-key`, `revoke-api-key`, `list-api-keys`.
- Migrations run at startup (`openDatabase` -> `db.Migrate`) and via `mailx migrate` (Compose one-shot service).

## Main flow (API send)

```
Developer -> REST API (auth, scope, validate, optional Idempotency-Key)
  -> FileStore write of raw MIME (BEFORE the DB tx; orphan file possible if tx fails)
  -> PostgreSQL tx: message + recipients + 'queued' event + outbox row (+ idempotency completion)   => HTTP 202
  -> dispatch poller: due outbox rows, ROUND-ROBIN across tenants (v0.31) -> Redis queue (duplicate-safe Enqueue; MarkOutboxDispatched)
  -> worker pool (N goroutines): claim -> load DURABLE state -> retry.Coordinator.Attempt
       -> delivery.Engine (DNS/MX -> transfer -> SMTP client)
  -> OutcomeStore.Persist (ONE PG tx): delivery_attempts row + messages.status + immutable event
  -> only then queue Ack / Release(next_retry_at)
  -> webhook fan-out (events.fanned_out_at IS NULL -> webhook_deliveries, one PG tx)
  -> webhook worker pool: lease claim -> decrypt secret -> signed HTTPS POST -> complete attempt
```
SMTP receive path (`:2525`) only parses and stores to FileStore; it does NOT create DB rows, outbox entries, or queue jobs (verified: `runSMTPReceiver` -> FileStore).

## HTTP surface (v1)

Auth: `Authorization: Bearer mx_<key_id>_<secret>` (not a JWT). Scopes: `emails:send`, `emails:read`, `domains:read`, `domains:write`,
`webhooks:read`, `webhooks:write`, `suppressions:read`, `suppressions:write`. Unauthenticated: `/health/live`, `/health/ready` (readiness = PostgreSQL AND Redis within 2 s total; 503 body names only `postgres`/`redis`, never raw errors), `/openapi.json`, `/docs`.
Operator listener (`MAILX_OBSERVABILITY_ADDR`, default `:9090`, separate from the API): `GET /metrics`, `/health/live` (no dependency calls), `/health/ready`; no `/v1`.
Routes: `POST /v1/emails`, `GET /v1/emails[/{id}]`, `/v1/domains` (+`/{id}`, `/{id}/verify`, DELETE), `/v1/webhooks` (+`/{id}`, `/{id}/rotate-secret`, `/{id}/deliveries`, DELETE), `GET /v1/events`, `GET /v1/domains/{id}/dkim` (+POST, `/verify`), `GET /v1/domains/{id}/spf`, `POST /v1/domains/{id}/spf/verify`, `GET /v1/domains/{id}/dmarc`, `POST /v1/domains/{id}/dmarc/verify`, `POST|GET /v1/suppressions`, `GET|DELETE /v1/suppressions/{id}`.
`POST /v1/emails` in v0.22: text/html body, to/cc/bcc, reply-to; **all recipients must share one domain (422 `mixed_recipient_domains`)**; attachments/tags/custom headers deferred.
OpenAPI is hand-written (`internal/api/openapi.go`) and guarded by a runtime drift test: API changes must update it.

## Database (PostgreSQL 16; migrations 000001-000014; forward-only fixes, applied migrations never edited)

Tables: `tenants`, `messages`, `recipients`, `delivery_attempts`, `events`, `outbox`, `api_keys`, `idempotency_keys`, `domains`,
`webhook_subscriptions`, `webhook_deliveries`, `webhook_delivery_attempts`, `dkim_keys`, `suppressions`. Message statuses: `queued, processing, retrying, delivered, failed, bounced, suppressed`; recipient statuses: `pending, delivered, failed, suppressed`.
Event types (internal): `queued, delivery_attempted, delivered, deferred, bounced, failed, suppressed`; public mapping: `email.queued, email.delivered, email.delivery_delayed, email.failed, email.bounced, email.suppressed` (`delivery_attempted` is never public).
IDs: application-generated crypto-random hex TEXT (no sequential IDs; avoids enumeration/volume leaks). `tenant_id` on every tenant-owned table.
Raw MIME and attachments are not in PostgreSQL. Indexes are justified by query patterns and checked by EXPLAIN tests (`explain_test.go`).
Note: migration 000014 (v0.31) replaced `idx_outbox_pending (available_at)` with `idx_outbox_pending_tenant (tenant_id, available_at) WHERE dispatched_at IS NULL` (see Abuse controls); its down migration restores the old index. Migration 000011 `webhook_deliveries` FKs `events(tenant_id,id) ON DELETE CASCADE`; subscriptions use `ON DELETE RESTRICT` (history retained; disable, not delete).

## Correctness invariants (each verified in code/tests/history)

1. **Accepted=true is never knowingly retransmitted.** `Accepted` = 2xx to DATA terminator (`internal/smtp/client.go`); `retry.Decide` returns TerminalSuccess whenever `Accepted` even if an error is present; delivery never opens a second connection after acceptance; worker reads durable state before SMTP and skips terminal messages.
2. **QUIT failure after DATA acceptance does not fail delivery** (`QuitError` recorded; engine returns nil error).
3. **MX fallback only for pre-session failures** (dial/greeting/EHLO/HELO); after MAIL/RCPT/DATA engagement the remote answer is final.
4. **Queue finalization (Ack/Release) happens only after the delivery outcome is durable.** `Pool.persistOutcome` retries PostgreSQL only (never re-enters SMTP), renews the claim lease each attempt, and on shutdown leaves the claim unfinalized for reclaim.
5. **PostgreSQL owns durable lifecycle truth.** Redis holds only scheduling + claim ownership; `retry.State` is rebuilt from `delivery_attempts` on reclaim (`databaseOutcomeStore.Load`, which also cross-checks stored decision vs result kind).
6. **Attempt + message status + event are one transaction** (`PersistDeliveryOutcome`), under `SELECT .. FOR UPDATE` on the message; replay of the same attempt is idempotent success; a new attempt after terminal returns `ErrMessageTerminal` (worker Acks, no SMTP). One outcome event per attempt (unique index, migration 000010).
7. **Transactional outbox:** HTTP 202 means message + outbox row are committed; dispatch to Redis is retried until done, independent of Redis availability at accept time.
8. **Retry is conservative:** unknown/zero-value decision = terminal; caller cancel/deadline = terminal; only temporary DNS/transfer failures retry; default 5 total operations, 30m base, 4h cap (values are policy defaults, not RFC mandates).
9. **Queue semantics are at-least-once**, duplicate active job ID is a no-op, Ack/Release/Renew are fenced by an ownership token (stale token rejected atomically in Lua).
10. **Tenant isolation:** every API resource is tenant-scoped in the query (tenant identity comes only from `authenticateMiddleware` via request context, never from client input). Idempotency scope is the tenant, not the key row, so rotation never breaks retries.
11. **Idempotency:** claim after validation, before FileStore write; completion in the same tx as message/outbox; completion requires matching fingerprint; different payload with same key => 409 (never echoes original); PostgreSQL is the sole arbiter.
12. **Event truth vs webhooks:** `events` is the only lifecycle source of truth; webhook tables track only notification obligations/attempts. A webhook failure cannot change message/attempt/event rows (separate tables; fan-out only sets `fanned_out_at`).
13. **Webhook delivery is at-least-once.** Stable event ID (`MailX-Event-Id`, envelope `id`) survives retries; consumers must deduplicate by `event_id`. `UNIQUE(subscription_id, event_id)` prevents double fan-out.
14. **Fan-out is atomic:** delivery rows + `fanned_out_at` in one tx (`FOR UPDATE SKIP LOCKED`); a subscription only receives events with `occurred_at >= subscription.created_at` (no backfill).
15. **Customer endpoints never execute in the email delivery path:** delivery worker and webhook workers are separate pools; the only coupling is the `events` table.
16. **Webhook lease fencing:** `lease_token` guards `CompleteWebhookAttempt`; expired leases are reclaimed and the abandoned attempt is marked `retrying`/`lease_expired`; CHECK constraint ties `delivering` to lease columns.
17. **DSN safety:** DSNs use null reverse-path; a DSN is never generated for a null-sender message; DSN carries original headers only, never the body.
18. **Recipient tracking is envelope-based**, not header-based (hidden Bcc is envelope-only; `header_kind` NULL).

## Observability (v0.23; observers only, never a source of truth)

- Logs: `log/slog` JSON (default) or text on stderr. Fields are stable IDs and bounded categories only: request_id, tenant_id, message_id, job_id, attempt, event_id, delivery_id, subscription_id, smtp `session_id` (process-local, no security meaning). Never logged: bodies/MIME, addresses, domains, URLs, secrets, signatures, Authorization, remote SMTP/HTTP text, panic values. A panicking log sink is swallowed (`safeHandler`).
- HTTP: request-ID middleware is OUTERMOST (recover is inside it) so panics still produce one access log + metric; route label is the matched mux pattern or `unmatched`.
- Components take optional `WithLogger`/`WithMetrics` (default discard/nil); `smtp.Config.Observer` for SMTP; `RedisQueue.Ping/Depth` are concrete read-only methods (`queue.Queue` unchanged).
- Metrics (namespace `mailx`, <=3 labels, allowlisted values else `other`): `build_info{version,commit}`, `http_requests_total{method,route,status_class}`, `http_request_duration_seconds{method,route}`, `smtp_sessions_total{result}`, `smtp_active_sessions`, `smtp_messages_total{result}`, `delivery_attempts_total{kind,decision}`, `delivery_attempt_duration_seconds{decision}`, `queue_operations_total{operation,result}`, `queue_depth`, `queue_depth_errors_total`, `webhook_attempts_total{outcome}`, `webhook_attempt_duration_seconds{outcome}`, plus Go/process collectors.
- The operator listener also runs in SMTP-only mode (no `DATABASE_URL`); readiness there has no dependencies to check.
- Webhook claim: one active claim per tenant is enforced with a per-tenant advisory lock plus a re-check after the lock (READ COMMITTED), not just a NOT EXISTS guard. Webhook creation maps resolver failures to a stable 503 and never returns resolver detail.
- Invariants: metrics/logging failure never alters SMTP, queue, DB, event, or webhook behavior; no logs table, no migrations (still 11).
- Worker errors passed to `WithOnError` are internal-infrastructure errors only; the recipient address was removed from the worker's "not addressable" error text.

## Outbound SMTP TLS (v0.24; design: `docs/design-v0.24.md`)

- Flow: 220 -> EHLO (HELO fallback on 5xx) -> capabilities -> policy -> `STARTTLS` (must be 220) -> reject if bytes follow the 220 -> `s.caps = nil` -> `tls.Client(raw).HandshakeContext` (bounded) -> swap I/O to TLS conn -> EHLO again (no HELO fallback) -> new capabilities -> MAIL/RCPT/DATA. `raw` never changes (deadline watcher race-free); `conn` is the I/O conn.
- Policy `MAILX_SMTP_TLS_POLICY`: `opportunistic` (default: TLS if advertised, plaintext only when NOT advertised) or `required` (never sends a message without verified TLS; fails before MAIL FROM). No silent downgrade: refusal (even 5xx), malformed reply, handshake or verification failure, or post-TLS EHLO failure fails the attempt; no plaintext retry on that connection or by reconnecting.
- Verification always on: system roots (+ `MAILX_SMTP_TLS_CA_FILE` extra roots), validity, server-auth EKU, MX host name (`ServerName` = host of the MX address). NOT verified: that the MX is the right MX for the recipient domain (unauthenticated DNS; no DANE/MTA-STS). No `InsecureSkipVerify` in production code. TLS min 1.2 (equals Go default).
- Bounds: `DialTimeout`, per-read `ReadTimeout`, `TLS.HandshakeTimeout` (30 s default), caller context (cancel sets a past deadline on the raw conn; close_notify write bounded to 1 s).
- Errors: stages `starttls`, `tls_handshake`, `ehlo_tls`; always `Temporary`; `TLSFailure.Error()` is a bounded category (raw x509/TLS text only via Unwrap). Delivery engine `decideFallback` returns `tryNext` for these stages (all before MAIL FROM); if all MX fail, kind is `KindTransferTemporary` and the existing retry engine reschedules.
- Observability: `mailx_smtp_tls_sessions_total{policy,outcome,version}` (allowlisted; 11 outcomes: established, not_offered, required_unavailable, rejected, handshake_timeout, verify_failed, handshake_failed, connection_lost, ehlo_failed, canceled, protocol_error; versions 1.2/1.3/other/none); worker `delivery_outcome` adds `tls_policy`, `tls_outcome`, `tls_version` from the last MX tried.
- Invariants added: capabilities from before a handshake are never used after it; `Accepted=true` over TLS is never retransmitted even if QUIT/teardown fails (tested at client and worker-pipeline level); liveness/readiness never depend on remote SMTP/TLS; the inbound listener does not advertise STARTTLS (tested).
- Deployment: the Docker runtime image installs `ca-certificates` (alpine ships none, which would have broken all peer verification including HTTPS webhooks).

## Outbound SMTP AUTH / trusted relay (v0.25; design: `docs/design-v0.25.md`)

- Flow: ... EHLO again (post-TLS) -> AUTH advertised in THAT reply? -> PLAIN (preferred) or LOGIN -> 235 -> MAIL FROM. Credentials imply TLS-required regardless of `MAILX_SMTP_TLS_POLICY`; no STARTTLS, refused STARTTLS, handshake or certificate failure all end the attempt before any AUTH byte. Mechanism chosen only from post-TLS capabilities (both `AUTH x y` and legacy `AUTH=x y` spellings). PLAIN uses the initial response unless the command would exceed the line limit, then the challenge form. CRAM-MD5, DIGEST-MD5, XOAUTH2/OAUTHBEARER, SCRAM unsupported.
- Routing: `delivery.Config.Relay` (nil = direct). Relay mode routes every delivery to the one configured relay (no MX lookup, no credentials-bearing path anywhere else, no fallback to direct on any failure). Direct mode resolves MX hosts and carries no credentials. `delivery.Result.Transport` = direct|relay. Config: `MAILX_RELAY_HOST` (enables), `MAILX_RELAY_PORT` (587), `MAILX_RELAY_USERNAME`, `MAILX_RELAY_PASSWORD`; invalid combinations are startup errors that name variables, never values. Compose and `.env.example` carry no credentials.
- Errors/retry: stage `auth`; SMTP semantics kept on the DeliveryError (454 temporary, 535/534 permanent, transport failures temporary); the engine treats every auth failure as temporary (`stopTemporary`, never another MX) because it describes relay configuration, not the message; existing backoff (30m..4h, 5 operations) bounds retries (tested: 20 jobs with wrong credentials = one AUTH attempt each, retries >= 20 minutes out). No separate AUTH retry system.
- Secrets: `smtp.Credentials` redacts under every fmt verb and slog; remote AUTH reply text is discarded (codes only); per-Send and per-engine copies; value-free validation errors (255-byte limit, no CR/LF/NUL). Base64 payloads are treated as secrets and searched for in logs, metrics, errors and persisted results in tests.
- Observability: `mailx_smtp_auth_attempts_total{mechanism (plain|login|none), outcome (success|rejected|temporary|no_tls|not_advertised|no_mechanism|protocol_error|connection_lost|timeout|canceled)}`; worker `delivery_outcome` adds `transport`, `auth_mechanism`, `auth_outcome`. Liveness/readiness never touch the relay.
- Invariants added: credentials never sent over plaintext or on stale pre-TLS capabilities; MAIL FROM unreachable before 235; direct MX delivery never authenticates (tested with a real MX that offers AUTH); relay failure never becomes direct delivery; AUTH success is not delivery (Accepted still needs final DATA 2xx; QUIT failure after acceptance keeps Accepted=true through the relay path).

## DKIM and verified-From (v0.26; design: `docs/design-v0.26.md`)

- Verified-From: `POST /v1/emails` requires the RFC 5322 From domain (parsed with `net/mail`, canonicalized by `domain.Normalize` via `domain.FromDomain`) to EXACTLY equal a verified, non-deleted domain of the authenticated tenant (`db.VerifiedSenderDomain`). No suffix or parent/subdomain inference; another tenant's or an unverified domain gives 403 `from_domain_not_authorized`. Runs before the idempotency claim, the FileStore write and every insert; `InsertMessage(SenderDomain)` re-checks FOR SHARE in its transaction. MAIL FROM is still the From address (bounce architecture unchanged). The API is the only outbound creator.
- Signing: `dkim.Sign` = rsa-sha256, 2048-bit, relaxed/relaxed, d=From domain (must equal the message From domain, exactly one From), signed headers from,to,cc,subject,date,message-id,mime-version,content-type,content-transfer-encoding,reply-to (present ones), tags v,a,c,d,s,t,h,bh,b only. Done at acceptance in the API after MIME is final and before storage: stored bytes = queued bytes = transmitted bytes (tested at a capturing MX for direct and relay, plus independent verification with go-msgauth). Retries resend the stored bytes; a message keeps its acceptance-time signature across key rotation.
- Keys: `dkim_keys` (migration 000012; FK to `domains(tenant_id,id)`; CHECK algorithm/size/selector/lifecycle; `uq_dkim_one_active`, `uq_dkim_one_pending`; `UNIQUE(domain_id,selector)`). Lifecycle pending (does not sign) -> active (after DNS TXT publication is verified by `POST .../dkim/verify`) -> retired (private ciphertext destroyed). Rotation = create a new pending key, publish, verify; the old key signs until activation. Selector `mx`+YYYYMMDD+4 hex. Domain deletion deletes keys in the same transaction; a re-claimed name starts with no keys.
- Storage/crypto: private key PKCS#8 DER -> AES-256-GCM (`internal/secretbox`, fresh nonce, AAD `mailx-dkim-v1|tenant|domain|selector`). `MAILX_DKIM_MASTER_KEY` (required, base64 32 bytes) must differ from `MAILX_WEBHOOK_MASTER_KEY` (enforced at startup); errors name variables not values. Webhook `SecretBox` now wraps the shared `secretbox`. Private keys are never in any API response, log, metric or error; keys live in process memory while used (Go cannot zeroize).
- Key creation is guarded: a domain with a pending key returns 409 before any RSA generation, and at most 2 generations run concurrently (cancellable wait).
- Failure behavior: a domain with an ACTIVE key always signs; missing/undecryptable/corrupt/mismatched key or signing failure => 503 `dkim_signing_unavailable`, nothing accepted or stored, never unsigned. A domain with no active key sends unsigned (DKIM not set up).
- API: `GET|POST /v1/domains/{id}/dkim`, `POST /v1/domains/{id}/dkim/verify` (domains:read/write, tenant-scoped 404); OpenAPI updated (drift test).
- Observability: `mailx_dkim_signatures_total{algorithm (rsa-sha256), outcome (signed|unsigned_no_key|key_unavailable|key_decrypt_failed|key_invalid|sign_failed|domain_mismatch)}`; nothing domain-, selector- or key-derived is logged or labelled.

## SPF sending-authorization guidance (v0.27; design: `docs/design-v0.27.md`)

- Purpose: help a tenant publish ONE correct SPF record and check it. It is guidance/readiness only: it never authorizes sending, never blocks sending, never evaluates a message, and never emits Received-SPF/Authentication-Results.
- SPF identity (verified in code): receivers check the envelope sender. MAIL FROM = the API From address (`email_handler.go`), so the record belongs on the tenant's own sending domain. Bounces use the null reverse path, for which receivers check HELO; MailX's HELO/EHLO is the constant `mailx.local` (`cmd/mailx/serve.go`), which cannot carry an SPF record (deliverability gap, v0.29). Header From and DMARC alignment are out of scope (v0.28).
- Sending infrastructure is operator-declared, never guessed: direct mode `MAILX_SENDING_IPS` (public IPv4/IPv6, max 16; loopback/private/link-local/CGNAT/documentation/multicast/reserved/ULA rejected at startup and again in `spf.NewService`); relay mode `MAILX_SPF_RELAY_INCLUDE` (a host name the relay provider documents). The other mode's variable is a startup error. Unset => status `sending_infrastructure_unknown`, actions `declare_sending_ips` / `follow_relay_provider`, no invented record. Local development needs neither.
- Verification (`POST /v1/domains/{id}/spf/verify`, domains:write, VERIFIED domain required, else 409; cross-tenant/unknown 404): one TXT lookup of the domain (5 s timeout, 16 concurrent lookups then 503 `spf_verification_busy`, <=64 TXT records, SPF record <=2048 bytes, <=64 terms, <=255 bytes/term, no regex/recursion). Statuses: `verified | not_configured | mismatch | conflict | invalid | temporary_error | sending_infrastructure_unknown | unchecked`, with bounded `reason` codes and `warnings` (`unevaluated_mechanisms`, `permits_all`, `dns_lookup_limit_risk`, `deprecated_ptr`). Temporary DNS failures (timeout, SERVFAIL, any resolver error) are never reported as misconfiguration. `GET /v1/domains/{id}/spf` (domains:read) returns guidance with NO DNS query.
- Record model: missing -> `create` `v=spf1 <ip4:/ip6: | include:relay> ~all`; existing single record -> `verified` only if it literally authorizes MailX (first matching literal ip4/ip6 with `+`, stopping at `all`; `~ip4:`, `-ip4:` and `+all` do not count), else `update_existing` = the SAME record with MailX's mechanisms inserted at the front; multiple SPF records -> `conflict`/`merge_records` (MailX never recommends a second record); merged output >2048 bytes is refused, not truncated.
- Lookup-limit decision: only the literal subset is evaluated. include/a/mx/exists/ptr/redirect are parsed, never followed (unbounded tenant-controlled DNS walking; RFC 7208 4.6.4 limit of 10). Such records report `mismatch` with `unevaluated_mechanisms: true`. `verified` never claims how a specific receiver will evaluate the record.
- Sending policy (DEC-054): missing/wrong SPF never blocks sending. Authorization = verified domain ownership; signing = active DKIM key; SPF = readiness info. SPF and DKIM state are independent (tested both ways); SPF cannot grant From authorization (tested: attacker cannot send from victim's domain even when SPF records authorize MailX).
- No persistence: DNS is the source of truth; no migration, no index. Observability: `mailx_spf_verifications_total{mode (direct|relay), outcome (statuses)}` allowlisted; no domain/tenant/IP/record/DNS-error label or log field. Health endpoints never touch SPF or public DNS.
- Structural boundary test: `internal/spf` may not import smtp/delivery/worker/dkim/queue/dispatch/secretbox; smtp/delivery/worker/dkim/dispatch/queue/retry/bounce may not import spf; `email_handler.go` must not mention SPF. So SPF cannot alter routing, relay credentials, STARTTLS, AUTH, signing or delivery truth.

## DMARC readiness (v0.28; design: `docs/design-v0.28.md`)

- Standard: RFC 9989 (with 9990/9991) obsoletes RFC 7489 (verified at rfc-editor.org). MailX follows it: `pct/rf/ri` removed (ignored, warning), `np/psd/t` parsed, multiple records discarded, unknown tags ignored, `v=DMARC1` first, `p` absent + valid `rua` acts as `p=none`. Tag names/values are matched case-insensitively (lenient ABNF reading).
- Sender-side only: no receiving-side evaluation, no Authentication-Results/DMARC-Signature, never blocks or authorizes sending, never claims a receiver result (`receiver_result` is always `not_observed`). DMARC cannot grant From authorization (tested); DKIM/SPF are consumed as facts and not modified (tested both ways).
- Identity model (verified in code/tests): From = verified tenant domain; MAIL FROM = the API From address (stored as `<local@Domain>`, case preserved, compared case-insensitively); DKIM `d=` = From domain; HELO `mailx.local` is irrelevant to DMARC SPF alignment (MAIL FROM only). Direct mode aligns exactly under strict and relaxed.
- Alignment (`align.go`): strict = identical canonical domains, no DNS; identical domains align in both modes with no DNS; relaxed = the two domains' Organizational Domains from the RFC 9989 DNS Tree Walk (never the PSL, suffix matching or label counting); unknown (not false) when DNS could not provide the boundary. With no published record, distinct names do not align (RFC default: the start domain is its own Organizational Domain). `canonical()` is only an ASCII LDH syntax gate; a test forbids `publicsuffix`, `internal/domain`, `strings.HasSuffix` and `EffectiveTLDPlusOne` in the package's production code.
- DNS Tree Walk (`treewalk.go`, RFC 9989 4.10/4.10.1/4.10.2; ONE walk from the From domain yields policy AND Organizational Domain): query `_dmarc.<name>` from the domain, then each parent down to the TLD (shortened to 7 labels when the name has 8+; max 8 queries per walked domain); records not starting `v=DMARC1` are discarded; multiple records at a name are ALL discarded and the walk CONTINUES; the walk stops at the first single record with `psd=n`/`psd=y` (a malformed record still counts, its psd read leniently). Organizational Domain: `psd=n` name; else `psd=y` (not the start's own) => one label below it; else the record-holding name with the fewest labels; else the start. Policy record: the domain's own, else the Organizational Domain's, else the PSD's (`psd=y`), never an intermediate record; `sp` applies before `p` when not the domain's own. DNS errors (other than no-record) abort the walk: no parent policy substituted, no guessed boundary, readiness `unknown`. MailX still reports `conflict` for multiple records at the domain (receivers silently fall back) or when nothing else governs, else warning `conflicting_records_discarded`. Sources: `domain|organizational_domain|public_suffix_domain`. Other identities are walked only when relaxed alignment needs them (never in MailX: d=, MAIL FROM and From are equal). Bounds: 5 s total, 16 concurrent verifications, 64 TXT records, 2048-byte record, 32 tags.
- Recommendation: `v=DMARC1; p=none` at `_dmarc.<domain>` (monitoring first). An existing policy is preserved (action `none`), never downgraded, never duplicated; conflict -> `merge_records`, invalid -> `fix_record`. No `rua`/`ruf` are ever generated (no report intake; ruf privacy-sensitive); `external_report_destination`, `failure_reporting_enabled`, `policy_not_enforcing`, `testing_mode`, `deprecated_tag` warnings.
- Status vocabulary: `dns.status` unchecked|not_configured|monitoring|enforcing|conflict|invalid|temporary_error; paths `dkim`/`spf` ready|not_configured|not_aligned|unknown; `readiness` ready|dns_action_required|authentication_incomplete|unknown|unchecked. `ready` = valid record AND at least one path aligned AND configured (DKIM: active key; SPF: direct mode + verified SPF): a precondition for a receiver DMARC pass, not proof. Relay mode: SPF path `unknown` (`relay_return_path_unknown`, empty identity) because the relay may rewrite the return-path; warning `relay_may_alter_signed_content`.
- API: `GET /v1/domains/{id}/dmarc` (domains:read, no DNS), `POST .../dmarc/verify` (domains:write, verified owned domain else 409, cross-tenant/unknown 404, stores nothing; also runs one SPF verification, which increments the SPF metric). Optional `api.Config.DMARC` (nil -> 503 `dmarc_not_configured`). No config variables, no schema, no index. Metric `mailx_dmarc_verifications_total{outcome,readiness}` allowlisted. Health never touches DMARC.
- Null reverse-path: DSNs are still not transmitted; if they ever are with `MAIL FROM:<>`, SPF would use `postmaster@<HELO>` = the configured SMTP hostname (v0.29; `mailx.local` only in local mode) which cannot align with a tenant From domain; only an aligned DKIM signature could give DMARC. DSN transmission is still out of scope.
- Boundary tests: `internal/dmarc` may not import smtp/delivery/worker/dkim/spf/queue/dispatch/secretbox; those and the send handler may not reference DMARC.

## Public SMTP identity (v0.29; design: `docs/design-v0.29.md`)

- Two identity layers, never conflated: a TENANT's verified domain controls From authorization, DKIM `d=`, SPF policy and DMARC alignment; the INFRASTRUCTURE hostname (`MAILX_SMTP_HOSTNAME`, the operator's, the PTR name of the sending IPs) controls EHLO/HELO, PTR/rDNS, forward DNS, Message-ID domain and the DSN Reporting-MTA. It is never derived from a tenant domain and tenants never create PTR records.
- Modes (`cmd/mailx/smtpidentity.go`): hostname set => validated strictly at startup (invalid => startup fails naming the variable and a reason code, never the value); `MAILX_SENDING_IPS` set => hostname REQUIRED (public direct SMTP never uses `mailx.local`); neither => local identity `mailx.local` (compose, tests, fake MX); relay without hostname => local identity with a startup warning. Startup is static only: DNS is never consulted, so a DNS outage cannot stop MailX; `/health/*` never depend on it.
- Validation (`smtpidentity.ValidateHostname`): ASCII, lower-cased, one trailing dot removed, nothing repaired; rejects empty/oversized/whitespace/control, non-ASCII and `xn--` (same IDN policy as domain ownership), IP literals, URLs, host:port, mailboxes, wildcards, `localhost`, reserved TLDs (`local`, `internal`, `lan`, `test`, `example`, `arpa`, ...), single-label, public-suffix-only, invalid labels and anything `domain.Normalize` refuses. Fuzzed.
- EHLO/HELO: one configured identity for the whole outbound session: EHLO before STARTTLS, EHLO after TLS and HELO fallback (byte-capture tests, also over the relay path); STARTTLS/AUTH semantics unchanged; the client still refuses identities with whitespace/CR/LF/NUL. Direct and relay use the same configured identity; MailX never checks PTR for a relay's IPs.
- Message-ID (source truth: MailX always generated it; the API accepts no user Message-ID or custom headers): now `<id@MAILX_SMTP_HOSTNAME>` (RFC 5322 3.6.4: domain of the generating host), built by one helper (`emailHandler.messageID`) used for the header and the stored metadata, before DKIM signing; stored signed bytes are never mutated. Local mode keeps `mailx.local`. `api.Config.MessageIDDomain` is checked as header-safe.
- PTR/forward-confirmed reverse DNS (`verify.go`): per configured IP `LookupAddr` then the hostname resolved once (A and AAAA). `ready` = a PTR name equals the hostname AND the hostname resolves back to the IP (membership); extra PTR names warn; states `missing_ptr|ptr_mismatch|forward_mismatch|malformed_ptr|oversized_dns_answer|temporary_error`; aggregate `ready` only if every IP is ready, `not_ready` on any definite failure, else `unknown`; deterministic order; a verdict under a finished context is never `ready`. Bounds: 16 IPs, 10 s, 4 concurrent reverse lookups, 16 PTR names, 64 forward addresses. IPv4 and IPv6 supported.
- HELO SPF (RFC 7208 2.3/2.4) is advisory: a single `v=spf1 ip4:.. -all` record at the hostname makes HELO-checked mail and bounce mail SPF-authenticated; missing => warning `helo_spf_not_verified`, never affects `ready`; tenant SPF/DKIM/DMARC semantics unchanged (the hostname is not a DMARC identity).
- Operator diagnostic, not an API: `mailx check-smtp-identity` (no arguments; reads `MAILX_SMTP_HOSTNAME`, `MAILX_SENDING_IPS`; live read-only DNS; exit non-zero unless ready). No tenant endpoint (PTR is the operator's; resolving caller-supplied names/IPs would be an SSRF-style probe), no OpenAPI, metric, schema or index change. `LocalInterface` (IP assigned to a local interface) is informational only.
- DNS agreeing with a configured IP proves DNS consistency, NOT that the machine really egresses from that IP (RSK-020 stays open; MailX never calls a third-party "what is my IP" service). Readiness never guarantees inbox placement.

- Database settings validation (v0.29 follow-up): at startup MailX reads `max_connections`, `superuser_reserved_connections`, `fsync`, `full_page_writes` and `synchronous_commit` (`database.DB.ServerSettings`) and logs `db_settings_warning` with a bounded `code` (`db_pool_exceeds_server_connections`, `db_fsync_off`, `db_full_page_writes_off`, `db_synchronous_commit_off`) when the pool (default 10) does not fit the non-reserved connections or durability is weakened; it never blocks startup and never touches DNS. Verified end to end: silent against the low-memory profile, four warnings against a deliberately weakened server. Opt-in memory profile: `compose.low-memory.yaml` (DEC-077); the default Compose file keeps stock PostgreSQL settings.

## Recipient suppression (v0.30; design: `docs/design-v0.30.md`)

- Meaning: durable tenant-scoped POLICY ("this tenant must not send to this address"), NOT a delivery fact. History is never rewritten by creating/deleting one. Table `suppressions` (migration 000013): `UNIQUE (tenant_id, email)` is both the concurrency control (`INSERT .. ON CONFLICT DO NOTHING`; first writer's reason/source win) and the hot lookup index; `idx_suppressions_tenant_created (tenant_id, created_at DESC, id DESC)` serves keyset listing. `reason` manual|hard_bounce|complaint|unsubscribe, `source` api|delivery|feedback (WHY vs HOW); only manual/api and hard_bounce/delivery are produced; complaint/unsubscribe/feedback are reserved (schema-ready for v0.32, refused by the API so callers cannot forge system facts). Evidence columns for hard bounces: `message_id`, `smtp_code`, `enhanced_status`.
- Key (`suppression.Normalize`, used by API, worker AND store): trim + one `<>` pair + one trailing domain dot; ASCII only; plain dot-atom local part; LDH domain, no IP-looking names; LOCAL PART LOWER-CASED FOR THE KEY ONLY (transport still preserves case; RFC 5321 2.4 discourages case-sensitive local parts and folding is the fail-safe direction for a deny list); dots and `+tag` are never folded (no provider rules). Every accepted recipient must be keyable (422 `invalid_recipient` at acceptance).
- Auto hard-bounce (`QualifiesHardBounce`, structured fields only): permanent + not accepted + stage `rcpt_to` + named recipient + 5xx + enhanced status 5.1.1 or 5.1.6. Never: 4xx/exhausted retries, MAIL FROM/DATA/AUTH/TLS stages, 5.7.x policy/authentication, 5.1.2/5.1.10 (domain), 5.1.3, 5.2.x, a bare 550, DNS failures. Written in the SAME transaction as the attempt/status/event (`PersistDeliveryOutcome(SuppressRecipient)`).
- Enforcement: (1) acceptance (`POST /v1/emails`, after authorization/signing, before storage): all recipients suppressed => 422 `all_recipients_suppressed`, nothing stored, the Idempotency-Key not consumed; partial => accepted; lookup failure refuses the request. (2) delivery (`worker.enforceSuppression`) once per attempt incl. retries, BEFORE the coordinator/any transport (direct and relay alike): suppressed recipients are removed from the envelope, all suppressed => zero SMTP connections. Implemented via `worker.SuppressionGate`, which the production `databaseOutcomeStore` implements (compile-time asserted); stores that do not implement it (test fakes) run without suppression.
- States: recipient `suppressed` (not failed/bounced); message terminal `suppressed` (all recipients suppressed, no attempt). Aggregation: all=>suppressed; +delivered=>delivered; +retrying=>retrying (later attempts skip them; all-suppressed between retries=>suppressed); +permanent failure=>failed. `RecordSuppressedRecipients` (rows + one event + terminal status) is one short transaction; the job is acked only after it commits; replays are idempotent (partial unique index `uq_events_message_suppressed`); it refuses to touch a delivered/failed message (`ErrMessageTerminal`): accepted history is immutable.
- Consistency boundary (truthful): a suppression created after the worker's check does not revoke an attempt already in progress; no DB lock is held across SMTP I/O. Guarantee: a recipient suppressed when the worker checks gets no SMTP attempt.
- Failure policy: unknown suppression state never means "send". Lookup or record failure => the job is deferred 15 s (`suppressionDeferral`), no SMTP, no attempt recorded, retry counters unchanged; cancellation is safe.
- API: `POST /v1/suppressions` (201 new / 200 existing, idempotent; only reason manual), `GET` list (keyset, `limit`, `cursor`, `email` filter), `GET|DELETE /v1/suppressions/{id}` (DELETE = hard delete, 204; no history change, nothing re-queued, `suppressed` messages stay terminal). Scopes `suppressions:read|write` (never implied by others). Errors `invalid_email`, `invalid_reason`, `suppression_not_found`, `all_recipients_suppressed`, `invalid_recipient`.
- Events: one lifecycle event `suppressed` (public `email.suppressed`) at most once per message, counts only (no addresses); list mutations are not events. Flows through the existing durable webhook fan-out; a webhook failure never changes suppression truth.
- Observability: `mailx_suppression_checks_total{result clear|partial|all|error}`, `mailx_suppression_writes_total{reason,source}` (allowlisted); no address/tenant/domain/message label; health unchanged; no Redis cache (PostgreSQL is the only source of truth).
- Measured (EXPLAIN ANALYZE, BUFFERS, 120,000 rows over two tenants): recipient lookup Index Only Scan on the unique index 0.031 ms/14 buffers; worker join 0.016 ms; list index-ordered, no sort, 0.014 ms; end-to-end benchmark ~0.36 ms per delivery attempt including the PostgreSQL round trip.

## Abuse controls (v0.31; design: `docs/design-v0.31.md`)

- Purpose: make legitimate sending safer (limit blast radius of a compromised key, runaway client, or one tenant starving others). NOT a reputation system, content filter, ML, billing, or warm-up.
- Tenant is the primary boundary. `requestLimitMiddleware` (after `authenticateMiddleware`, so unauthenticated requests never spend a bucket) charges a TENANT bucket and the API KEY's guard bucket in ONE atomic call (all-or-nothing); key limit <= tenant limit is validated, and every key charges the tenant bucket, so extra keys never raise a limit. 429 `tenant_rate_limited` / `api_key_rate_limited`.
- Algorithm: GCRA (token-bucket equivalent) in one Redis Lua script; time is Redis `TIME` (one clock); exactly ONE `EVALSHA` per decision; `{tenant}` hash tags for Cluster; every key has a PX TTL (idle keys vanish); per-call timeout.
- Send path (`POST /v1/emails`), after validation/signing/suppression and after the idempotency claim is owned: `admitSend` = tenant undelivered cap (`CountTenantQueued`, bounded count of queued+processing+retrying; 429 `tenant_queue_full`) -> global backlog (`CountPendingOutbox`; 503 `system_busy`) -> recipient bucket charged per DELIVERABLE recipient (suppressed recipients are free; 429 `recipient_rate_limited`). Any refusal calls `ReleaseIdempotencyClaim` (guarded by fingerprint AND claim time, so a reclaimer's claim is never deleted) so the same Idempotency-Key is reusable after Retry-After. Replays and same-key/different-body 409s are decided BEFORE any charge. Per-message recipient max = `MAILX_LIMIT_MAX_RECIPIENTS`.
- 429 = the tenant/key exceeded its limit (Retry-After exact for rate limits; fixed 30 s for queue-full). 503 = system capacity or the limiter cannot answer (Retry-After 5 or 30). Both send `Retry-After` in whole seconds; bodies use the standard error shape and never carry tenant/key/address data.
- Failure policy: limiter (Redis) error on a send or any mutating request => FAIL CLOSED 503 `rate_limiter_unavailable`; on GET => fail open (metric + log). PostgreSQL count errors => 500. Worker permit state unknown => defer 15 s, no attempt. `MAILX_ABUSE_CONTROLS=off` is the only opt-out (loud warning); any other non-`on` value fails startup.
- Delivery: `worker.acquirePermits` (after suppression, before coordinator/transport; needs `worker.TenantLookup`, implemented by `databaseOutcomeStore`) takes a per-tenant then per-destination-domain lease (ZSET holder->expiry; holder = job id + claim token, so a reclaimed job holds its own permit). Every 503 carries `Retry-After` (default 5 s). Refused => `p.release` with a jittered 5 s delay: NO attempt recorded, retry counters unmoved, no SMTP. Permits are released with a fresh context (cancellation/shutdown safe); a crashed worker's permit expires by `MAILX_LIMIT_PERMIT_TTL`.
- Fair dispatch: `ListPendingOutbox` = recursive loose index scan of tenants (cap 200) + LATERAL per-tenant oldest rows + rank interleave (round robin); `FOR UPDATE SKIP LOCKED` removed (implicit tx made it a no-op; Enqueue is duplicate-safe, MarkOutboxDispatched guarded). Migration 000014 swaps the index (both indexes together made the planner filter 15,000 rows behind a big backlog; tenant-index-only: 0.062 ms at 30,000 rows).
- Retry jitter: `BackoffPolicy.JitterPercent` (0-50) applied in `NextSchedule` via `Jitter(delay, seed)` (FNV of the scheduling instant: deterministic, <= Max, >= 1 s); same helper spreads permit deferrals.
- Observability: `mailx_abuse_control_decisions_total{control request|recipient|tenant_queue|backpressure|tenant_permit|destination_permit, outcome allowed|limited|unavailable|impossible|deferred}` (unknown -> `other`; max 30 series); logs never carry tenant/key/address/domain.
- OpenAPI (`openAPIServed`) adds `429 RateLimited` to every operation and `503 Unavailable` to every mutating one, both with a `Retry-After` header, plus the idempotency/abuse text on POST /emails; drift-tested.
- Measured: limiter adds ~0.31 ms/request serially (Redis round trip in a Docker VM; 0.09 ms at 4 CPUs), +30 allocs/1.4 KB; fair dispatch 1.2 ms per 100-row batch (20 tenants); bounded queued count 0.30 ms (500 rows). Low-memory profile: unaffected (PostgreSQL 34.6 MiB, Redis 4.2 MiB, app 8.1 MiB during a 60-send smoke).

## Security decisions (verified)

- API secrets never stored raw: only `key_id` + HMAC-SHA256(pepper, secret); 256-bit random secret makes slow password hashing pointless; unkeyed SHA-256 fallback without pepper is a documented dev-only choice. All auth failures collapse to one generic 401; DB error on auth fails closed. No public key-creation endpoint (CLI bootstrap).
- Webhook signing secrets need recoverable storage => AES-256-GCM with `MAILX_WEBHOOK_MASTER_KEY`, tenant ID as associated data (`webhook/secret.go`); secret returned only at create/rotate; `whsec_` prefix.
- Signature: `MailX-Webhook-Signature: v1=hex(HMAC-SHA256(secret, timestamp + "." + body))`, signed bytes = sent bytes; `VerifySignature` enforces 5-minute tolerance and constant-time compare.
- SSRF: `URLPolicy.Validate` at create/rotate AND `URLPolicy.DialContext` re-resolves and re-validates at connection time and dials the validated address (closes DNS rebinding). HTTPS only, no userinfo/fragment, blocks private/loopback/link-local/multicast/CGNAT/doc/reserved ranges; no proxy; redirects not followed; 4 KiB response cap; 10s total timeout. `MAILX_WEBHOOK_ALLOW_INSECURE` relaxes all of it (dev only).
- Domain ownership: 256-bit token TXT proof; Normalize rejects wildcard/IP/IDN/`xn--`/non-ICANN/public-suffix names; pending claims by multiple tenants allowed so squatters cannot block the real owner; verified ownership unique per name.
- Outbound MIME: CRLF/header-injection rejection on every user-controlled field; Bcc never appears in headers.
- SMTP receiver: bounded line/message/connection/recipient/time limits.
- Compose: loopback-only host ports, non-root image, dev-only credentials.

## Worker / concurrency

Delivery: exactly `MAILX_WORKERS` goroutines, bounded queue capacity (Enqueue blocks at capacity = backpressure), panic recovery per job, `bookkeepingTimeout` 5s, half-lease cap on persistence timeout.
Redis queue polling (200ms..2s), not blocking primitives (multi-condition wake-up). Webhook: fan-out poll 250ms (batch 100, immediate loop when full), workers default 4, claim lease 30s, max 8 attempts, backoff 1m doubling to 1h with equal jitter, `Retry-After` honored (cap 1h). 2xx = success; 408/429/5xx/network = retry; other 4xx = terminal.

## Known limitations and technical debt (verified present at HEAD)

1. **Remote acceptance -> hard crash before local persistence** remains ambiguous: SMTP and PostgreSQL cannot share a transaction; the message may be re-sent after reclaim. No exactly-once SMTP (documented in code).
2. **DSNs are generated but never transmitted** (`worker.handleTerminalFailure` builds/serializes then discards). A terminal failure emits a `failed`/`bounced` event, but the sender gets no bounce email. Also `handleTerminalFailure` runs after outcome persistence and is not itself durable.
3. **Webhook delivery is at-least-once, no manual replay** (deferred), no global ordering guarantee across events/endpoints.
4. **Process-local retry state** (`stateStore`) survives only as a cache; durable state is authoritative on every job (v0.20-era note about memory-only state is superseded by `57ee1d0`).
5. (Resolved in v0.26) Verified-From is enforced at the API boundary. Remaining: no per-domain "require DKIM" flag (a domain requires DKIM exactly when it has an active key); no automatic key expiry or scheduled rotation; no explicit key deletion endpoint; Ed25519 and header oversigning deferred; no DKIM DNS re-check after activation.
6. (Resolved in v0.23) Readiness now checks PostgreSQL and Redis; metrics and structured logs exist. Remaining: no tracing, no log/metric shipping, metrics endpoint unauthenticated (bind to loopback/private network only), `queue_depth` is scraped live from Redis each scrape.
7. **Mixed-domain recipients rejected** (one delivery domain per message); recipient-level partial success is not modeled (RCPT is all-or-error).
8. **No inbound STARTTLS and no inbound SMTP AUTH** (outbound STARTTLS exists since v0.24); IDN/A-label domains unsupported in DNS and domain ownership. Outbound TLS gaps: no DANE/MTA-STS, so MX-to-domain binding relies on DNS; default opportunistic policy fails closed on a peer that advertises STARTTLS with an untrusted or mismatched certificate (no unverified-encryption mode); TLS facts are logs/metrics only, not persisted per attempt.
9. **FileStore write precedes DB commit** in the API path: a failed tx can leave an orphan message directory (deliberate and documented as harmless in `email_handler.go`: the reverse, a DB row without bytes, cannot happen; no reaper exists). Raw MIME lives on local disk (single-node storage).
10. **SMTP receiver is not wired to the outbox/queue**: inbound mail is stored, not relayed.
11. Attempt limits/backoff are fixed defaults (5 ops, 30m/4h); only the jitter spread is configurable (`MAILX_RETRY_JITTER_PERCENT`, v0.31).
12. PostgreSQL integration tests use `MAILX_TEST_DATABASE_URL` when set, otherwise a local default DSN, and **skip** if unreachable; Redis tests **fail** if Redis is unreachable. Neither self-provisions. Validation runs must set the DSN explicitly or DB coverage is silently lost.
13. `newMux` (`internal/api/routes.go`) falls back to a zero-key `SecretBox` when no `routeServices` are passed. Production always passes a real webhook service (`api.Config.Webhooks` is required), so this is a test-scaffold footgun, not an active bug.
14. Webhook secret has a single master key and no key-versioning/rotation path for the master key.

## Superseded (do not treat as current)

- Pre-v0.31: the dispatcher read the outbox in global `available_at` order under `FOR UPDATE SKIP LOCKED` on `idx_outbox_pending`, so one tenant's backlog could delay every other tenant's messages; there were no request, recipient, queue-depth or concurrency limits and retry times were exactly `Base*2^n`. Superseded by round-robin dispatch (migration 000014), abuse controls and jittered retries.

- Pre-v0.30: every accepted recipient could be sent to regardless of history; a permanent RCPT rejection only failed that one message and the same dead address would be tried again by the next message. Superseded by tenant suppression (auto hard-bounce + manual).

- Pre-v0.29: outbound EHLO/HELO, generated Message-IDs and the DSN Reporting-MTA were the constant `mailx.local` for every deployment; superseded by the configured public hostname (local mode keeps `mailx.local`).

- v0.28 first commit (`c4b5882`): the DMARC Organizational Domain came from the ICANN Public Suffix List (RFC 7489 model) with a separate PSL-bounded policy walk; superseded by the RFC 9989 DNS Tree Walk (DEC-066). The PSL remains only in `internal/domain` for ownership validation.

- Pre-v0.26: outbound mail from any From domain was accepted (v0.21 recorded ownership but did not enforce it) and every message was sent unsigned.
- Pre-v0.24: outbound SMTP was always plaintext; the client sent MAIL FROM straight after the first EHLO and its context watcher set deadlines on the (single) connection field.
- Pre-v0.23: ad-hoc `log.Printf` logging (including full inbound message bodies/addresses in the SMTP sink), PostgreSQL-only readiness with raw error text in the 503 body, and `withRecoverMiddleware` outside the request-ID middleware.
- v0.18 worker "best-effort status reporter after Ack/Release" -> replaced in `57ee1d0` by transactional `OutcomeStore` persisted before finalization.
- v0.18 temporary `devTenantMiddleware` -> replaced by API-key `authenticateMiddleware` in v0.19.
- v0.15 `recipients UNIQUE(message_id, address)` -> `(message_id, address, header_kind)` (migration 000003).
- v0.19 partial index `idx_api_keys_tenant_active` -> superseded by 000008 tenant/created_at index.
- v0.16/v0.20 statements that retry state is process memory -> superseded by durable reconstruction (`57ee1d0`).
15. Relay credentials live in the process environment and memory for the process lifetime (Go strings cannot be zeroed); no `_FILE` secret input, no rotation without restart. Implicit-TLS relays (port 465), OAuth/XOAUTH2 and SCRAM are unsupported; one relay for all domains and tenants.
17. SPF (v0.27): egress addresses must be declared by the operator (no discovery; NAT/gateway/IPv6 privacy addresses are the operator's job); only the literal ip4/ip6 (direct) or named include (relay) subset is verified, so records that authorize MailX only via include/a/mx/exists/redirect show `mismatch`; HELO is `mailx.local` (no SPF/PTR-alignable HELO until v0.29); relay return-path rewriting is provider-specific and unmodelled; SPF result is not persisted or shown in the message/event history.
18. DMARC (v0.28): readiness only; no aggregate/failure report intake or external report-destination authorization check; no policy progression tooling; relay return-path/DKIM behavior unmodelled beyond `unknown`; DSN/null-reverse-path DMARC deferred; a DMARC verify triggers an SPF verification; a verify costs up to 8 DNS queries per walked domain (one domain in practice) plus the SPF lookup.
19. Hosted Redis: `queue.RedisConfig` has a `Password` field and `redis.Options` could take TLS, but `cmd/mailx/serve.go` passes only `REDIS_ADDR` (host:port): no password, no TLS. A managed Redis/Valkey that requires TLS and a password (for example Aiven) is unsupported without a code change. PostgreSQL works with a hosted service through `DATABASE_URL` (pgx accepts `sslmode`); the pool default is 10 connections (`database.defaultMaxConns`), relevant for plans with a low `max_connections` (Aiven free: 20).
19b. SMTP identity (v0.29): egress IP is unproven (RSK-020); the inbound receiver greeting is still `220 localhost MailX SMTP Server` (inbound out of scope; no Received headers are generated); PTR targets that are CNAMEs are not detected (RFC 1912); DSNs are not transmitted so bounce identity is not exercised; one identity is used for direct and relay.
20. Suppression (v0.30): RCPT is still all-or-error, so one bad recipient fails the whole message (v0.30 only prevents the repeat by suppressing it); per-recipient delivered/failed states are not modeled; no complaint/unsubscribe/feedback producer (v0.32); no bulk import/export; hard delete leaves no audit trail of removals; no global/cross-tenant suppression (v0.31 abuse controls); case variants of a local part are one key by design; messages accepted before v0.30 with unkeyable recipients stay deliverable.
21. Abuse controls (v0.31): limits are per ACCOUNT (destination concurrency is per domain, destination RATE is not limited); no per-route weights, warm-up, automatic suspension, or complaint/bounce-rate breaker; charged recipient tokens are not refunded if PostgreSQL fails after the charge; more than 200 simultaneously backlogged tenants are served in tenant-id order per dispatch batch (RSK-031); sending and delivery depend on Redis for limiting (fail closed, RSK-032); a permit TTL shorter than one attempt lets that tenant briefly exceed its concurrency limit (RSK-034); RSK-029 (one bad recipient fails a multi-recipient message) is unchanged.
16. DKIM master key lives in the environment like the webhook key (no `_FILE` input, no re-encryption tooling for master-key rotation); losing it makes stored DKIM keys undecryptable and domains with an active key refuse to send until rekeyed.


## Outbound feedback (v0.32; DSNs and complaints)

- Boundary: `POST /internal/feedback`, NOT under `/v1`, authenticated by a constant-time-compared operator bearer token (`MAILX_FEEDBACK_INGEST_TOKEN`), not a tenant API key. Not general inbound email: no mailbox, no IMAP/POP3, no arbitrary routing — it accepts only feedback about a message MailX already sent. Deployment: the operator runs their own bounce-mailbox/provider-webhook relay and forwards JSON here; MailX does not yet operate a public bounce-receiving MTA (deferred, RSK).
- Parser `internal/feedback` (pure, no DB): `ParseDSN` reads RFC 3464 multipart/report -> message/delivery-status per-recipient field groups (Final-Recipient, Original-Recipient, Action, Status, Diagnostic-Code, *-MTA), bounded (256 KiB input, 16 MIME parts/groups), never panics (fuzzed). `Classify` maps Action+Status (RFC 3463 enhanced status, reusing `bounce.ParseEnhancedStatus`) to bounce_permanent/temporary/unknown; never trusts human-readable text.
- Correlation: `feedback.Correlator` issues/verifies an HMAC-SHA256 token binding a MailX message ID (already 128-bit crypto-random, `storage.NewID`). The ingest route accepts either a verified token or a bare `message_id` — the latter is safe ONLY because the whole route requires the operator credential; tenant is always re-derived server-side from the message row, never from request input (tested: forged/guessed message IDs cannot touch another tenant). VERP-style Return-Path correlation was evaluated and DEFERRED (RSK): MAIL FROM is unchanged, preserving all v0.24-v0.29 SPF/DKIM/DMARC/identity guarantees; it needs a dedicated bounce-receiving domain MailX does not yet operate.
- Classification/suppression rule (mirrors v0.30's `QualifiesHardBounce`): new `suppression.QualifiesAsyncHardBounce(enhanced)` — only 5.1.1/5.1.6 on a permanent DSN suppress; 4.x.x (delayed), unknown/malformed DSNs, and any other 5.x.x (e.g. 5.7.1 policy) never suppress. Complaints always suppress (`reason=complaint, source=feedback`, both reserved since v0.30).
- State model: SMTP transport truth (`delivery_attempts`, `messages.status`) is NEVER rewritten by feedback. Feedback lands on `recipients.feedback_status/feedback_at/feedback_enhanced_status` (migration 000015), a separate summary column set, transition-guarded (`feedback_status IS DISTINCT FROM`) so re-delivery of semantically identical feedback never re-fires suppression or events. `messages.status`/`StatusBounced`/`EventBounced` stay reserved as before (v0.32 does not activate the message-level bounced status — a single recipient's later bounce should not overwrite a multi-recipient message's coarse status).
- Persistence: `database.ProcessFeedback`, one transaction: `feedback` history row (migration 000015; UNIQUE(message_id, recipient_id, raw_sha256) is the idempotency key — exact-duplicate bytes are a no-op; a later different DSN about the same recipient is new history) -> recipient transition -> suppression (reused `suppressions` table/constraint) -> event (`EventBounced` reused, new `EventComplained`/`email.complained`) -> existing webhook fan-out (unchanged; feedback never depends on webhook success). recipient_id NOT NULL: unmatched feedback is refused, not stored as an orphan.
- Retention: `feedback` is classified historical/diagnostic (like `delivery_attempts`); no raw DSN bytes are stored, only normalized bounded fields; no cleanup job ships this milestone, but nothing blocks adding one later.
- Security: bounded parser (fuzzed), constant-time auth, HMAC constant-time token verify, tenant always server-derived, no raw DSN/tokens in logs or webhook payloads (webhook `data` allowlists `recipient`/`enhanced_status` only).
- Observability: no new metrics this milestone (deferred, RSK) — existing event/webhook metrics cover fan-out; feedback ingestion itself is not yet instrumented.
- Deferred/risk: RSK-035 no bounded metrics for feedback ingestion yet; RSK-036 VERP Return-Path correlation deferred (needs a bounce-receiving domain); RSK-037 no provider-specific complaint adapters implemented (JSON envelope only; provider-specific parsing would need its own adapter, none wired); RSK-029 (RCPT all-or-error) unchanged, not touched by v0.32.


## Reusable email templates (v0.33)

- Tenant-owned content (migration 000016, `templates` table): name (unique per tenant, DB constraint), subject, text_body, html_body, timestamps. Not retention-bound; lives until deleted.
- Renderer `internal/emailtemplate` (pure, no I/O): `{{identifier}}` substitution only — no text/template actions, no code execution, no filesystem/network access. Single linear pass, bounded output (2 MiB), no recursive expansion (a substituted value is never re-scanned). Missing variable -> empty string; malformed token (`{{1bad}}`, unmatched `{{`) -> left verbatim, never an error.
- HTML safety: variables substituted into html_body are `html.EscapeString`-ed; text/subject get the raw value. This is the only model v0.33 implements (documented explicitly, not claimed "safe" beyond this).
- Send integration: `POST /v1/emails` gains `template_id`+`variables`, mutually exclusive with subject/html/text (422 `template_and_content_conflict`; `variables` without `template_id` is 422 `variables_without_template`). Rendering happens in `handleSend`, once, BEFORE `outbound.Build`/DKIM — never re-rendered by workers or retries. Subject CRLF-injection protection is unchanged (`outbound.Build`'s existing `rejectControlChars`, which sees whatever subject it is given, templated or not).
- Idempotency: `idempotency.Fingerprint` hashes the ORIGINAL request struct (template_id+variables), never the rendered output — `handleSend` keeps `req` unmutated and only overrides local `subject/text/html` variables. Editing a template between an accepted request and a same-key retry does not change the fingerprint, so the retry correctly replays the durably-stored ORIGINAL rendered message (`loadReplay` reads `messages`, never re-renders). Different variables/template_id -> different fingerprint -> existing 409 conflict behavior, unchanged.
- CRUD: `POST/GET /v1/templates`, `GET/PATCH/DELETE /v1/templates/{id}`, keyset pagination (mirrors suppressions). Scopes `templates:read`/`templates:write` (new DB CHECK on `api_keys.scopes`, migration 000016). Cross-tenant access is 404 (existence never leaked).
- Delete/update: hard delete, no versioning (deferred if ever needed). Deleting/editing a template never touches already-accepted messages (separate storage: FileStore + `messages` row already hold the rendered bytes).
- Retention: durable tenant configuration, not delivery telemetry (like domains/suppressions, not delivery_attempts).


## Contacts (v0.34)

- Tenant-owned durable data: "this tenant knows this recipient" (migration 000017, `contacts` table). Independent of suppression (safety policy) and message recipients (SMTP transport state) — no FK between them either direction, no cascade.
- Identity: `internal/contact.Normalize` — deliberately NOT `suppression.Normalize`. Same domain rules (ASCII, lower-cased, one trailing root dot stripped, LDH labels) but LOCAL PART CASE IS PRESERVED (suppression folds it as a deny-list safe direction; a contact must not silently merge two distinct mailboxes). No provider-specific folding (no Gmail dot/plus-tag).
- Uniqueness: `UNIQUE(tenant_id, normalized_email)`, a DB constraint (not just app logic) — tested under 10-way concurrent create, exactly one succeeds. Duplicate create is 409, no upsert in v0.34.
- Attributes: flat `map[string]string`, stored JSONB, bounded (20 entries, 64-char keys, 500-char values, 8192-byte serialized CHECK backstop). No nesting, no arrays, no arbitrary JSON.
- API: `POST/GET /v1/contacts`, `GET/PATCH/DELETE /v1/contacts/{id}`, keyset pagination (mirrors templates/suppressions). Scopes `contacts:read`/`contacts:write` (new `api_keys.scopes` CHECK, migration 000017).
- Suppression independence (explicitly tested): a suppressed address can still become a contact; deleting a contact never deletes its suppression; recreating a contact never resets/removes a suppression; changing a contact's email never migrates the suppression (it stays keyed on the old address); deleting a suppression never deletes the contact.
- Sending is unaffected: `POST /v1/emails` requires no pre-existing contact, and v0.34 does NOT auto-create contacts from sends (deliberate, avoids implicit CRM behavior).
- Delete: hard delete, no versioning. Update: partial (PATCH); changing email re-validates + re-checks the NEW identity's uniqueness.
- Templates: NOT coupled to contacts in v0.34 — no automatic attribute injection into template variables (deferred to a future Broadcasts design).
- Events/webhooks: no `contact.*` events added — deliberate, avoids scope creep; CRUD has no delivery-pipeline consequence to notify about.
- Metrics: none added — CRUD is already covered by generic HTTP observability; no contact-specific operational signal identified yet.
- Retention: durable customer data, kept until the tenant deletes it (unlike delivery telemetry, not retention-bound).
- Deferred: bulk import (CSV/batch), audience/segmentation queries, GIN indexes on attributes — no query needs them yet.


## Audiences (v0.35)

- Named groups of existing Contacts, membership only — no sending, no queue jobs, no MIME/DKIM/SMTP (migration 000018: `audiences`, `audience_members`).
- Many-to-many via `audience_members` (audience_id, contact_id, tenant_id), PK(audience_id,contact_id) for uniqueness. Tenant integrity is DB-enforced, not just app-checked: composite FKs `(tenant_id,audience_id)->audiences(tenant_id,id)` and `(tenant_id,contact_id)->contacts(tenant_id,id)` (new `UNIQUE(tenant_id,id)` added to both tables) make a cross-tenant membership row structurally impossible. `database.AddAudienceMember` also pre-checks both resources under the SAME transaction for a clean, non-disclosing 404 instead of a raw FK-violation error.
- Cascade: `audience_members` rows cascade on EITHER audience delete or contact delete (both FKs `ON DELETE CASCADE`) — deleting an audience removes only membership rows (contacts untouched); deleting a contact removes only its membership rows (audiences untouched). Neither touches suppressions (tested both directions).
- Uniqueness: `UNIQUE(tenant_id,name)` on audiences (409 on duplicate, DB-enforced). Membership add is idempotent (matches suppression's create-if-absent convention): re-adding an existing member is a 204 no-op, never a duplicate row or an error.
- API: `POST/GET /v1/audiences`, `GET/PATCH/DELETE /v1/audiences/{id}`, `POST/GET /v1/audiences/{id}/contacts`, `DELETE /v1/audiences/{id}/contacts/{contact_id}`. Scopes `audiences:read`/`audiences:write` (new `api_keys.scopes` CHECK).
- Membership listing is keyset-paginated by the membership row's own (created_at, contact_id) — not the contact's own created_at — so pagination is stable regardless of when the contact was originally created; naturally supports v0.36 iterating a large audience in bounded pages without loading it all into memory.
- Suppression independence (tested): a suppressed contact can be added to an audience; removing/audience-deleting never touches suppression state.
- No sending: v0.35 has no send endpoint, creates no queue jobs, never renders templates or invokes DKIM/SMTP. v0.36 (Broadcasts) will decide separately how/when to snapshot a mutable audience's membership for a send.
- Events/webhooks: no `audience.*` events added — deliberate, no consumer yet.
- Metrics: none added — CRUD already covered by generic HTTP observability.
- Retention: durable tenant configuration, kept until explicitly deleted (like contacts/templates, not delivery telemetry).


## Broadcasts / bulk sending (v0.36)

- Orchestration ONLY over the EXISTING send pipeline (MIME/DKIM/outbox/queue/worker/SMTP unchanged): a broadcast never becomes one giant SMTP transaction — each recipient becomes its own normal `messages` row via the SAME `database.InsertMessage` POST /v1/emails uses.
- State machine (`broadcasts.status`): accepted -> expanding -> completed | failed. "completed" means every recipient was either suppressed or handed to the existing pipeline — NEVER delivered/inbox placement. "failed" is used only for a whole-broadcast condition (From domain no longer verified), never for one bad recipient.
- Two durable phases per (broadcast, contact): SNAPSHOT (`broadcast_recipients` row: contact_id/email/name/attributes copied once) then MATERIALIZE (render -> MIME -> DKIM -> `InsertMessage`, status pending->suppressed|materialized). `internal/broadcast.Expander` (mirrors `internal/dispatch`'s outbox-polling pattern) advances both phases in bounded per-tick batches (200 audience rows / 25 recipients), never the whole audience in memory or one transaction.
- Audience snapshot semantics: `broadcasts.audience_snapshot_at` is stamped by PostgreSQL's `now()` at acceptance (not Go's clock — avoids Go/DB clock skew, found and fixed during testing). Expansion only ever reads `audience_members` rows with `created_at <= audience_snapshot_at`, so a contact added afterward is NEVER included, however long expansion takes (tested). A member removed from the audience before its batch is scanned is a documented narrow race (RSK-038), not a correctness bug.
- Template snapshot: `broadcasts.subject_template/text_template/html_template` copy the Template's CURRENT source at acceptance; the live `templates` table is NEVER re-read during expansion (tested: edited-then-deleted template still produces the original frozen content for every recipient, mutation-checked).
- Personalization: `broadcast_recipients.attributes`/`name` are copied at snapshot time (not re-read from the live Contact later); materialization merges broadcast-level `variables` with the recipient's own snapshot (recipient wins on key collision), reusing v0.33's `emailtemplate` renderer unchanged.
- Crash safety / internal idempotency: snapshot insertion uses `ON CONFLICT (broadcast_id,contact_id) DO NOTHING` (re-scanning the same audience range after a crash creates no duplicates); `broadcast_recipients.id` doubles as the eventual `messages.id`, so materialization checks "does a message with this id already exist" before ever charging quota or calling InsertMessage again (a crash between InsertMessage succeeding and the recipient status update is a safe idempotent retry, tested). `MarkBroadcastRecipient{Suppressed,Materialized}` guard on `status='pending'` so a stray duplicate transition is a no-op, never overwrites a terminal state.
- HTTP acceptance (`POST /v1/broadcasts`): validates audience/template ownership and From-domain verification, then ONE bounded INSERT — no recipient rows are created synchronously, no rendering, no signing. Reuses v0.20's exact idempotency pattern (`ClaimIdempotencyKey`/poll/replay, fingerprint on the ORIGINAL request) — an accepted request retried with the same key after the Template was edited still replays the original broadcast, never creates a second campaign (tested).
- Suppression: reused authority (`suppression.Normalize` + `SuppressedForTenant`), checked LATE — immediately before materialization, not just at acceptance — so a suppression created while a broadcast is still expanding still stops any not-yet-materialized recipient (tested). Suppressed recipients consume zero quota and zero SMTP attempts.
- Abuse controls: materialization charges the SAME tenant recipient bucket as `/v1/emails` (`ratelimit.TenantRecipientKey`) and respects the same `CountTenantQueued`/`CountPendingOutbox` backpressure before each batch; a refusal leaves recipients `pending` for a later tick (this IS the broadcast's backpressure/fairness mechanism — it never bypasses v0.31, it proceeds more slowly). API keys cannot multiply broadcast throughput (same tenant-scoped accounting).
- Tenant isolation: every DB query tenant-scoped; audience/template ownership validated authoritatively in `handleCreate`, not merely because auth passed; cross-tenant references are 404, never disclosing which resource was missing/foreign (tested both directions).
- Cancellation: DEFERRED (not implemented) — explicitly documented rather than faked; a partial/fake cancel that still lets workers send would be worse than none.
- API: `POST/GET /v1/broadcasts`, `GET /v1/broadcasts/{id}/recipients` (keyset). No PATCH, no DELETE (deliberately omitted — see limitations). Scopes `broadcasts:read`/`broadcasts:write`.
- Feedback/events: no `broadcast.*` events or bounce truth store added — materialized recipients are normal messages, so v0.32 feedback and existing `email.*` events already apply via the message's own id; `BroadcastRecipient.message_id` is the correlation handle.
- Metrics: `mailx_broadcast_expansion_batches_total{phase,outcome}` (bounded: 3x5 series). No broadcast/tenant/contact id ever labeled.
- Retention: `broadcasts`/`broadcast_recipients` are durable historical/operational records (like `delivery_attempts`), not auto-expired; deleting a broadcast is not implemented, so no cascade-into-history risk exists yet.
- Indexes (measured, 100k audience_members / 50k broadcast_recipients synthetic, throwaway container): snapshot query is an index-only scan via `idx_audience_members_audience_created`, bounded to the batch LIMIT (0.58ms). Pending-recipient query initially chose the WRONG index (`idx_broadcast_recipients_broadcast_created`, filtering ~43k non-pending rows, 87k buffer reads, 15ms) because the first partial index design (`(broadcast_id) WHERE status='pending'`) lacked `created_at` for ordering; fixed by adding `created_at` to the partial index -> 756 buffer reads, 4ms (~115x fewer buffer reads). Recorded as a real, found-and-fixed design flaw, not a hypothetical.

## Scheduled sending (v0.37; design decisions: DEC-125..133)

- Scope: normal email (`POST /v1/emails` `scheduled_at`) and Broadcasts (`POST /v1/broadcasts` `send_at`). Neither is a new sending pipeline — scheduling only controls WHEN already-existing durable work becomes runnable.
- Normal email: reuses the pre-existing `messages`/`outbox.available_at` mechanism, present since v0.18 (`internal/api/email_types.go`'s `sendEmailRequest.ScheduledAt` -> `database.NewMessage.AvailableAt` -> `outbox.available_at`) — this milestone's audit found it already implemented but untested and Go-clock-authoritative; both gaps are now closed.
- Broadcast: `broadcasts.send_at` (nullable `TIMESTAMPTZ`, migration 000020) gates the EXISTING v0.36 expander: `ClaimActiveBroadcasts` now requires `status IN ('accepted','expanding') AND (send_at IS NULL OR send_at <= now())`. A future-dated broadcast is simply invisible to the poller until due — no second scheduler, no new status value.
- Wire format: RFC 3339 absolute instant only (`internal/api/scheduling.go`'s `parseSendAt`, shared by both handlers), rejected if unparsable or in the past. No natural-language/bare-time parsing, no named-timezone infrastructure — an offset already identifies an absolute instant.
- Clock authority: EVERY due-work decision (outbox and Broadcasts) is PostgreSQL-clock-authoritative, computed inside SQL (`available_at <= now()`, `send_at <= now()`). `ListPendingOutbox`'s Go `now time.Time` parameter was REMOVED in this milestone (previously the sole Go-clock comparison in the send path) — same lesson v0.36 already learned from its acceptance-watermark skew (DEC-127).
- No-early-send: proven for both paths — `TestListPendingOutboxExcludesFutureAvailableAt`, `TestScheduledBroadcastNotExpandedBeforeSendAt` — and mutation-checked (removing the due predicate makes the test fail, confirmed and reverted).
- Broadcast snapshot timing: UNCHANGED from v0.36 — `audience_snapshot_at` is stamped at ACCEPTANCE regardless of `send_at` (DEC-128). Scheduling a broadcast for later therefore does NOT widen RSK-038: a contact added to the Audience after acceptance is excluded whether the broadcast sends immediately or a week later (`TestScheduledBroadcastSnapshotIsAtAcceptanceNotActivation`).
- Template/contact freeze: unaffected — v0.36's acceptance-time snapshot (subject/text/html copied into the broadcast row; recipient email/name/attributes copied into `broadcast_recipients`) already means scheduling changes nothing about WHAT was accepted, only WHEN expansion may begin.
- Suppression/abuse: NOT frozen at scheduling time. Both remain evaluated at their existing late boundaries — suppression immediately before materialization (Broadcast) / at dispatch (normal email); abuse/quota accounting at materialization/dispatch, same tenant-scoped buckets as immediate sends. A schedule created Monday carries no bypass for Friday's safety state (DEC-129).
- Restart/downtime: no additional recovery path needed — a scheduled row is ordinary durable Postgres state (`outbox`/`broadcasts`), found by the SAME polling queries dispatch/expansion already run every tick; a crashed or restarted process simply resumes polling and any now-due row becomes eligible, exactly like the pre-existing v0.15/v0.36 crash-recovery model. No new crash window was introduced.
- Concurrency: unaffected — outbox dispatch was already duplicate-safe (JobID + idempotent `MarkOutboxDispatched`), and `ClaimActiveBroadcasts`'s `FOR UPDATE SKIP LOCKED` (unchanged) still prevents two expander instances claiming the same broadcast.
- Idempotency: `send_at`/`scheduled_at` are ordinary fields in the fingerprinted request struct (`idempotency.Fingerprint` hashes the whole validated request) — a retry with the same Idempotency-Key but a different scheduled time is a 409 conflict, not a silent reschedule (tested both paths).
- Reschedule/cancel: NOT implemented (DEC-130). `send_at` is immutable after acceptance, same posture as v0.36's broadcast-configuration immutability (DEC-123). Deferred rather than adding unsafe/racy cancel semantics (RSK-039 unchanged).
- Fairness/backpressure: unaffected — a large overdue backlog is still bounded by the SAME per-tick batch sizes (outbox's fair round-robin batch, expander's 200/25 batches); scheduling introduces no new unbounded-selection path.
- Indexes: `idx_broadcasts_active_due (send_at, created_at) WHERE status IN ('accepted','expanding')`. EXPLAIN at 2003 active broadcasts (2000 future-scheduled, 3 due): bitmap index scan, 8 buffer hits, 0.018ms — no sequential scan (`TestClaimActiveBroadcastsDueScanAtScale`, MET-072).
- API: no new scopes — reuses `emails:send`/`broadcasts:write`. OpenAPI documents `scheduled_at`/`send_at` on both request and response schemas, including the "eligibility boundary, not exact delivery time" semantics.
- Deferred/out of scope: maximum future horizon (none enforced beyond Postgres `timestamptz` range), domain/DKIM re-validation at activation (unchanged from v0.36's acceptance-time check — not revisited), scheduler-specific observability metrics beyond the existing dispatch/expansion metrics, scheduling for anything other than emails/Broadcasts.

## Default retry backoff is front-loaded (ad-hoc, 2026-09-22; DEC-143/144, supersedes the reverted urgent-priority tier DEC-140..142)

- `retry.DefaultBackoffPolicy()` is `Schedule: [5s, 5min, 30min, 2h]` — exactly 4 entries, ONE PER DELAY between `DefaultAttemptLimit`'s 5 operations (a 5th entry would be unreachable: the delay after the last allowed attempt is never scheduled, since exhaustion follows immediately — PR review caught an earlier 5-entry version whose trailing 5h entry was dead code, DEC-144). Applied to EVERY send, no opt-in field. `BackoffPolicy.Delay` checks the new `Schedule []time.Duration` field first; the older `Base`/`Max` exponential-doubling path (still used by any caller constructing its own `BackoffPolicy{Base, Max}`) is unchanged and used only as a fallback when `Schedule` is empty.
- Why: the previous single default (30min/1h/2h/4h/4h) made a transient first-attempt failure functionally fatal for time-critical mail (OTPs, password resets) — see the conversation's diagnosis of a real test send to iCloud that hit a transient DNS timeout and sat unretried for 30 minutes. An earlier iteration added an opt-in `priority: "urgent"` field (DEC-140..142); reverted after feedback that requiring every caller to remember to flag time-critical sends is bad ergonomics for MailX's users. This is the simpler, universal fix.
- Total exhaustion window is ~2h35m across the 4 real delays — SHORTER than the old ~7.5h, a deliberate accepted tradeoff of front-loading (DEC-144), not an oversight: bulk/marketing mail's later retries (30min, 2h gaps) are still exactly as polite as before, just abandoned sooner overall.
- Tests: `TestDefaultBackoffPolicy` (retry) asserts the exact 4-entry schedule (`len == DefaultAttemptLimit().MaxAttempts-1`, guarding against a future unreachable-entry regression), that Delay(1) is under 5 minutes (the OTP-window sanity check), and that attempts beyond the schedule's length repeat the last entry rather than growing unbounded or erroring. Updated every test that hardcoded the old default's specific delay values (`internal/retry/{coordinator,schedule,integration}_test.go`, `internal/queue/integration_test.go`) and one worker test whose "no retry storm" threshold assumed the old ~30-minute first delay (`internal/worker/auth_pipeline_test.go`, now asserts >=3s instead of >=20min — the real invariant being tested, no tight zero-delay hammering loop, is unaffected).
- Dev-environment note (unrelated code fix, same session): `compose.yaml`'s `mailx` service now pins `dns: [1.1.1.1, 8.8.8.8]` — Go's `CGO_ENABLED=0` static build uses its own pure-Go DNS resolver, which is flaky against Docker Compose's embedded DNS proxy (127.0.0.11) for external lookups (spurious ~8s timeouts reproduced live against icloud.com's MX during manual testing, not reproducible with `nslookup`/`getent` in the same container). This is a local dev-compose mitigation only, not a production concern.

## Advanced Analytics (v0.38; design decisions DEC-148..156)

- Pure read layer over the EXISTING `events` table (`internal/database/analytics.go`) — no new table, no OLAP infrastructure, no cache. `events` already records queued/delivered/deferred/bounced/failed/suppressed/complained, one row per lifecycle transition, tenant-scoped, timestamped by `occurred_at`, already indexed via `idx_events_tenant_occurred (tenant_id, occurred_at DESC, id DESC)`.
- Three endpoints, `analytics:read` scope (migration 000022, not implied by any other scope): `GET /v1/analytics/overview?from=&to=`, `GET /v1/analytics/timeseries?from=&to=&interval=hour|day`, `GET /v1/analytics/broadcasts/{id}`.
- Metric vocabulary (exact predicates in `analytics.go`'s package doc): "delivered" = remote SMTP accepted final DATA (2xx) — NEVER inbox placement, spam-folder avoidance, or a human reading the message. Facts are NOT mutually exclusive: an earlier `queued`/`delivered` fact for a message is never erased by a later async `bounced`/`complained` fact (DEC-149) — both are counted, preserving real history. `CurrentlySuppressed` is a current-state snapshot (`count(*) FROM suppressions`), deliberately separate from the time-bucketed historical counts (DEC-150).
- Time range: `[from,to)` half-open RFC 3339, capped at 90 days (`AnalyticsMaxRange`). Timeseries buckets ("hour"|"day", UTC) are sparse — an empty interval is simply absent, never zero-filled (DEC-152) — and bucket count is capped at 744 (`AnalyticsMaxBuckets`), rejected analytically from the request BEFORE the query runs, not just from the result size (DEC-151, so a huge future range with zero current events still gets rejected).
- Broadcast analytics reads `broadcast_recipients` (the durable snapshot, per v0.36) for intended/pending/suppressed/materialized/recipient_failed counts, plus an `events` join (via `broadcast_recipients.message_id`) for delivered/bounced/complained/failed among materialized recipients — NEVER live Audience membership (DEC-153, proven by a test that removes a member post-snapshot and mutation-checked).
- Consistency: near-current at query time, directly from PostgreSQL — no aggregate processor, so no eventual-consistency lag and no replay/idempotency machinery needed (DEC-156).
- Open/click tracking: explicitly deferred (DEC-155) — no pixels, no link rewriting, no `open_rate`/`click_rate` fields at all (omitted entirely, never a misleading zero).
- Tenant isolation: every query parameter-binds `tenant_id`; Broadcast analytics 404s for a cross-tenant id via the existing `broadcasts` ownership check. Mutation-checked (removing the tenant predicate breaks `TestAnalyticsOverviewTenantIsolation`).
- Indexes: zero new indexes — `idx_events_tenant_occurred` (pre-existing) already covers every analytics query. EXPLAIN evidence at 50k synthetic events spread across 90 days, queried with a selective 1-day window: index scan, 17 buffer hits, <0.15ms for both overview and timeseries (`TestAnalyticsHotQueriesUseIndexes`).
- Failure semantics: PostgreSQL unavailable → 500 per existing API convention; malformed/oversized range → 422; unknown/cross-tenant broadcast → 404; empty tenant → 200 with coherent zero values (never null, never an error).
- Does NOT close RSK-035 (feedback-ingestion parser/correlation OPERATOR metrics) — a distinct, still-open concern from this milestone's tenant-facing sending analytics; not silently conflated.
- Deferred/out of scope: domain-level and destination-provider analytics (high cardinality, misleading deliverability inference — DEFERRED per the spec's explicit guidance), contact engagement/lead scoring (not this milestone's job), AI-generated insights/recommendations, webhook-delivery analytics (separate from email delivery, not built).

## Sending Pools / Routing (v0.39; design decisions DEC-157..161)

- Three-layer model, kept deliberately distinct (DEC-157): configured POLICY (`sending_pools`/`sending_pool_members`, migration 000023, operator-mutable) vs the durable per-message ROUTING DECISION (`messages.sending_member_id`, set once at `InsertMessage` acceptance, immutable/retry-sticky by application convention) vs the per-attempt historical TRANSPORT SNAPSHOT (`delivery_attempts.{sending_member_id,transport_kind,effective_hostname,effective_source_ip}`, denormalized, no FK, survives later config changes). `messages` has NO `sending_pool_id` — only the member decision is durable there.
- Pools/members are operator-global infrastructure, CLI-only (`cmd/mailx/sendingpools.go`: `create-sending-pool`, `list-sending-pools`, `enable/disable-sending-pool`, `create-sending-pool-member`, `list-sending-pool-members`, `enable/disable-sending-pool-member`, `assign-domain-pool`) — no tenant-facing REST API, no tenant-writable `domains.sending_pool_id` (DEC-158). No pool/member deletion in v0.39; disable only, so a historical `sending_member_id` can never go dangling.
- Member kinds: `direct` (own `hostname`/`source_ip`, dials MX directly, gets its own `smtp.Client`/`delivery.Engine`) or `relay` (no per-member identity at all — reuses the SAME single process-wide `MAILX_RELAY_*` engine; no per-member credential storage, matching the existing single-relay-config architecture).
- Route/member selection happens ONCE, inside `InsertMessage`'s existing transaction, piggybacked on the pre-existing `SenderDomain` `FOR SHARE` domain check (now also reads `domains.sending_pool_id` there — no extra query). `internal/routing.SelectMember` (pure, no I/O) picks deterministically via `sha256(messageID) mod sorted(enabled member ids)`; a disabled pool, or a pool with zero currently-enabled members, degrades gracefully to the legacy no-pool path (`sending_member_id` stays NULL) rather than failing message acceptance — an operator misconfiguration must never block sending.
- `worker.processor.go` reads the durable `sending_member_id` via `DeliveryState`/`DurableDeliveryState` (extended, not re-derived) and sets it on `delivery.Request.MemberID`; `internal/routing.Router` (a `retry.Deliverer`, built once at `cmd/mailx/serve.go` startup from current pool/member config — process-local, takes effect on next restart, not live) dispatches by `MemberID`. `MemberID==""` (the legacy no-pool path) always uses the base `Engine`. A non-empty `MemberID` the registry does not recognize (added, or fixed, since the process started) is NEVER silently sent through base — that could dial the wrong source IP/EHLO identity or bypass a relay the operator intended (DEC-169/170, PR #18 review). `buildRouter` likewise only maps a `relay`-kind member to base when a relay is actually configured (`relayConfigured` — DEC-170); otherwise that member is omitted from the registry.
- `worker.holdIfMemberDisabled` checks `worker.MemberRegistryGate.MemberKnownLocally` FIRST, before `MemberRoutingGate`/before any SMTP work: an unrecognized member holds via the existing bounded `memberDisabledHold` release, exactly like a disabled member, spending ZERO retry attempts (DEC-174, PR #18 re-review). This matters because `retry.Coordinator` counts every `Deliver` call — including one that returns an error — as a real attempt against `DefaultAttemptLimit` (5); routing an unknown-member condition through the ordinary Deliver-error path (the first attempt at this fix, DEC-169) would exhaust and PERMANENTLY fail the message after 5 attempts, which is exactly the failure mode the kill switch exists to prevent. `routing.Router.Known(memberID) bool` and `databaseOutcomeStore`'s `*routing.Router` reference back this gate; `Router.Deliver`'s own error-returning unknown-member path remains only as defense-in-depth for callers without the registry gate wired.
- Disabled-member kill switch (DEC-159, corrected from the initial proposal): `worker.holdIfMemberDisabled` runs BEFORE any SMTP work when a message's durable member (or its pool) is disabled — zero SMTP, zero attempt records, `sending_member_id` untouched, job released via the existing claim/outbox mechanism with a fixed 30s bound (`memberDisabledHold`, never 0/unbounded, so a disabled member cannot cause a hot retry loop), resuming through the SAME member once re-enabled. v0.39 has NO failover/rotation logic at all — this is what keeps a disabled member from being an evasion path around receiver policy/reputation.
- Per-attempt transport snapshot (DEC-160): `routing.Router.Deliver` sets `delivery.Result.Effective{Hostname,SourceIP,MemberID}` only on the actual member-dispatch path (never the legacy fallback); `cmd/mailx/outcome_store.go`'s `Persist` copies these plus `Result.Transport` ("direct"/"relay", pre-existing, set by every `Engine`) into `NewDeliveryAttempt`. Never a secret/credential.
- `internal/smtp.ClientConfig.SourceIP` (prerequisite groundwork, done before the schema/routing work) is REAL dialer configuration — `NewClient` sets `net.Dialer.LocalAddr` when non-nil, proven portably (without relying on a second bindable loopback address, which macOS does not alias the way Linux does) by asserting a bind failure against an unassigned TEST-NET-3 address (`TestClientSourceIPIsWiredIntoDialer`).
- Migration-upgrade compatibility fix (DEC-161): `InsertMessage`/`PersistDeliveryOutcome` only reference the new columns when a value is actually set, keeping the legacy INSERT statement byte-for-byte identical to pre-v0.39 — required by this package's own migration-upgrade regression tests, which insert with CURRENT Go code against a schema missing the 1-2 most recent migrations (rolling-deploy-safety invariant). Also fixed: `pgx` cannot scan `inet` into `*string` directly — every such read wraps the column in `host(...)`.
- Deferred/out of scope (explicitly, do not start before v0.40): weighted routing, adaptive/reputation-based routing, per-pool queues or worker pools, automatic IP warming, automatic reputation failover, arbitrary tenant-controlled source IPs or relay endpoints, a new secret-storage architecture, any tenant-facing sending-pool API.

## BIMI brand indicators (v0.40; design decisions DEC-162..168)

- `internal/bimi` gives sender-side BIMI readiness for a domain, following the same posture as `internal/dmarc`/`internal/spf`: DNS is the source of truth, nothing is persisted, no migration (DEC-162). `Store`/`TXTResolver`/`DMARCState`/`Observer` seams mirror dmarc's `Store`/`TXTResolver`/`DKIMState`/`SPFState` pattern exactly; `cmd/mailx/bimiconfig.go`'s `dmarcState` adapter wraps the existing `dmarc.Service.Verify` and maps only `EffectivePolicy`/`OrgDomain`/`Checked` — BIMI never re-implements DMARC evaluation.
- DNS record: `default._bimi.<domain>` TXT (`v=BIMI1; l=<https URL or empty>; a=<https URL, optional>`), falling back to the DMARC Organizational Domain if the domain itself published nothing (DEC-164: only the `default` selector is checked — MailX has no per-message BIMI-Selector concept). `l=` empty is "declined" (an explicit no-logo statement), distinct from "not_configured" (no record at all).
- DMARC prerequisite: effective policy must not be `none` — no separate `pct=` check, since MailX's RFC-9989 DMARC already discards that tag entirely (DEC-163; this differs from some RFC-7489-era BIMI guidance, a deliberately conservative documented conflict resolution).
- SVG logo validation (`ValidateSVG`, opt-in via `?validate_assets=true`) checks the security-relevant SVG Tiny 1.2 Portable/Secure subset MailX can truthfully verify: version/baseProfile, square viewBox, required title, and the absence of script/foreignObject/image/style/animate elements and any external href — bounded (32KB, depth 64, 20000 nodes), no entity expansion (DEC-165). This is a structural/security check, not full-profile certification.
- Certificate (VMC/CMC) handling (`ParseCertificate`) is structural-only: `crypto/x509` parse + NotBefore/NotAfter window, reporting Subject/Issuer/CurrentlyValid. No chain building, no revocation check, no BIMI-authority trust anchor, no private CA, no private-key storage (DEC-166). Readiness treats a parseable but expired/not-yet-valid certificate as `certificate_issue`, not `ready` (DEC-171, PR #18 review).
- Asset fetching (`AssetFetcher`) reuses `internal/webhook.URLPolicy`'s DNS-rebinding-safe `DialContext` rather than a second SSRF implementation; adds HTTPS-only (no insecure override), a hard size cap (bounded to `MaxCertificateBytes`, the larger of the two asset caps, so a certificate between the logo and certificate limits still reaches the parser — `ValidateSVG` separately enforces the tighter `MaxLogoBytes` bound on whatever bytes it receives, DEC-173), and follows zero redirects (the draft doesn't specify redirect handling for `l=`/`a=`, so MailX takes the conservative reading) (DEC-167).
- DNS lookup errors distinguish a definitive "no record" from a transient resolver failure (SERVFAIL/timeout) via `*net.DNSError`'s `IsNotFound`/`IsTemporary`/`IsTimeout`, matching `internal/spf`/`internal/dmarc`'s existing pattern — only a definitive not-found is `not_configured` (and eligible for the organizational-domain fallback); anything else is `temporary_error` (DEC-172, PR #18 review).
- API: `GET /v1/domains/{id}/bimi` (describe, no DNS, `domains:read`) and `POST /v1/domains/{id}/bimi/verify?validate_assets=true` (DNS + DMARC + optional asset checks, `domains:write`, requires a verified domain), mirroring DMARC's endpoint shape exactly. Every response carries a mandatory `disclaimer` field: MailX readiness is never a display guarantee — mailbox providers retain full discretion (DEC-168, enforced structurally via the OpenAPI required-field list, not just prose).
- Readiness states (factual, not a score): `unchecked`, `not_configured`, `declined`, `invalid_record`, `dmarc_prerequisite_failed`, `logo_issue`, `certificate_issue`, `ready`, `unknown` (DNS temporary failure).
- Deferred/out of scope: custom/per-message BIMI selectors, any BIMI-authority CA trust store or revocation checking, a private CA or key-issuance system, automatic logo generation, receiving-side BIMI evaluation, any claim about actual mailbox-provider display.

## Batch Sending (v0.41; design decisions DEC-175..180)

- `POST /v1/emails/batch` accepts up to `MaxBatchSize` (100, DEC-178) independent emails in one call — distinct recipients/content each, NOT v0.36 Broadcasts' one-template-to-one-audience shape. No schema/migration: batch items become ordinary `messages`/`outbox` rows, indistinguishable from a single send once accepted — there is no "batch" concept anywhere below the API layer.
- Implementation is a pure API-layer refactor, not a new pipeline (DEC-175): `emailHandler.acceptOne(ctx, tenantID, req, idemKey, now, scheduledAt) (email, replayed bool, *apiError)` holds the ENTIRE per-message acceptance sequence — template render, `outbound.Build`, From-domain authorization + DKIM signing (`authorizeAndSign`), recipient suppression check (`checkRecipientsForAcceptance`), the idempotency claim, `admitSend` abuse controls, the FileStore write, and the durable `InsertMessage` — extracted unchanged from the pre-v0.41 `handleSend`. Both `handleSend` (one item) and `handleSendBatch` (N items, one per loop iteration) call it. `authorizeAndSign`/`checkRecipientsForAcceptance` were changed to return `*apiError` instead of writing directly to `http.ResponseWriter`, since a batch caller must attribute a failure to one item's result slot without corrupting the shared HTTP response. The full pre-existing single-send test suite (109 tests) passed unchanged after this refactor.
- Independence, transactional and abuse-control (DEC-176): each item is its own `acceptOne` call — its own FileStore write, its own `InsertMessage` transaction, its own `admitSend` check. No batch-level transaction, no shared/batched abuse-control budget: a batch of N items can never buy a tenant more throughput than N individual `POST /v1/emails` calls would have (the tenant queue cap and recipient rate limit still bite mid-batch — proven by a dedicated test). PARTIAL FAILURE is the contract, never all-or-nothing: one item's rejection never blocks its siblings; every item gets exactly one result, at its own array index, in request order.
- Idempotency is per-item, not per-batch-request (DEC-177): no batch-level `Idempotency-Key` header (inherently single-valued per HTTP request); each item may carry an optional `idempotency_key` JSON field instead, reusing the exact same `idempotency.Fingerprint`/`ClaimIdempotencyKey`/replay machinery the header-based path already drives, via the shared `acceptOne`. A malformed per-item key (or an oversized/empty batch) rejects the WHOLE request before any item is processed — verified by asserting zero messages exist afterward.
- Response: `{data: [{index, email?, error?}], accepted, rejected}` — `error` mirrors the top-level error envelope's `{type, code, message}` shape (no `request_id`, which is a whole-request concept). Always HTTP 202 (the call itself succeeded; check each item's own outcome).
- Deferred/out of scope: no batch-level transaction/atomicity option, no per-tenant/per-plan batch-size tuning (no plan/tier concept exists yet in this codebase), no async/webhook-only batch result delivery (the full result set is always returned synchronously in the 202 body).
- Request-rate-limit charge is proportional to batch size (DEC-179, PR #19 review): `requestLimitMiddleware` charges Cost:1 per HTTP request regardless of body size, which let one token buy up to 100x the DKIM/DB work of a normal send. `handleSendBatch` now charges the SAME tenant/API-key request buckets the remaining `N-1` tokens BEFORE any per-item work runs; a refusal rejects the whole batch (429) with zero items touched. A single-item batch charges nothing extra.
- Batch-wide processing deadline (DEC-180, PR #19 review): `pollIdempotencyCompletion` can block up to 5s per item on an in-progress key; sequential across up to 100 items this could exceed `writeTimeout` (15s) and silently drop unprocessed items when the connection closes. `emailHandler.batchBudget` (defaulted to 10s, a field like `now` so tests can inject a near-zero budget deterministically) bounds the whole loop; once spent, remaining items get an explicit `batch_processing_timeout` result rather than being attempted or silently dropped.

## SMTP Submission (v0.42; design decisions DEC-181..184)

- `cmd/mailx/submission.go`'s `runSubmissionReceiver`: implicit-TLS listener (`crypto/tls.Listen`), disabled unless `MAILX_SUBMISSION_ADDR`+`MAILX_SUBMISSION_TLS_CERT`+`MAILX_SUBMISSION_TLS_KEY` are all set (DEC-181). Distinct from the pre-existing unauthenticated dev-receiver on port 2525 (`runSMTPReceiver`), which is untouched.
- `internal/smtp.Config.RequireAuth`/`Authenticator`: AUTH PLAIN only, inline form; MAIL FROM refused (530) until authenticated (DEC-182). Authenticator wraps `auth.Service.Authenticate` + an `emails:send` scope check.
- `api.SubmissionAcceptor` (`internal/api/submission.go`) wraps the unexported `emailHandler.acceptOne` so submitted mail goes through the IDENTICAL pipeline `POST /v1/emails` uses — no second accept path (DEC-183).
- Verified end-to-end with a real TLS SMTP client before commit, not just unit tests (DEC-184's bug — disabled-receiver-crashes-server — was only caught this way).

## Open & Link Tracking (v0.43; design decisions DEC-185..189)

- Opt-in per send (`track_opens`/`track_clicks`, off by default), reusing the existing `events` table with two new types (`opened`,`clicked`, migration 000024) — no new aggregate table, consistent with v0.38's posture and v0.38's own deliberate deferral reasoning (DEC-155).
- No durable per-link table: `internal/tracking` issues self-contained HMAC-signed tokens (tenant/message/recipient/URL) via `MAILX_TRACKING_SECRET`; the click redirect can never be an open redirect since MailX itself signed the exact destination at send time (DEC-186). Unconfigured (`MAILX_TRACKING_SECRET`/`MAILX_TRACKING_BASE_URL` unset) silently no-ops rather than producing broken links.
- `emailHandler.injectTracking` (regexp-based `href` rewrite + pixel append) runs in `acceptOne` after template rendering, before `outbound.Build`/DKIM signing — so the tracked HTML is what actually gets signed and sent. Links containing "unsubscribe" are never rewritten (DEC-187; MailX has no unsubscribe-link feature yet to special-case further).
- `GET /track/open/{token}` (1x1 GIF) and `GET /track/click/{token}` (302) are PUBLIC routes (outside `/v1`, no auth), registered only when a tracking secret is configured.
- Attribution uses `req.To[0]` only — MailX's regular send path shares one rendered body across all RCPT, so true per-recipient attribution isn't resolvable without per-recipient rendering (DEC-188).
- Deferred: webhook subscription-side `email.opened`/`email.clicked` support (DEC-189), template-level tracking defaults, HTML-parser-based (vs regexp) link rewriting.

## Deliverability Insights (v0.45; design decision DEC-195)

- Pure extension of v0.38's read-only analytics layer (`internal/database/analytics.go`, `internal/api/analytics_handler.go`) — no new tables, no new writes, no new event types.
- `AnalyticsCounts` (shared by overview and timeseries) gained `Opened`/`Clicked`, sourced from v0.43's existing `opened`/`clicked` event types.
- `GET /v1/analytics/overview` response gained a `rates` object (`delivery_rate`, `bounce_rate`, `failure_rate`, `complaint_rate`, `open_rate`, `click_rate`), server-computed as count/`queued` (queued is the only stable denominator — see the non-mutually-exclusive-facts doc in analytics.go). All-zero when `queued` is 0.
- New `GET /v1/analytics/domains?from=&to=` — `database.DomainBreakdown` groups CURRENT `recipients.status` (not the historical events stream) by recipient email domain, joined through `messages` for tenant scope and filtered by `recipients.created_at`. Ordered by total desc, capped at 50 rows (`AnalyticsMaxDomains`). Domain extraction trims a trailing `>` since real recipient rows are stored in raw `<addr>` header form.

## Official SDKs (v0.44; design decisions DEC-190..194)

- `sdk/node` (TypeScript, `@mailx/sdk`), `sdk/python` (`mailx_sdk`), `sdk/go` (Go module `github.com/Ferousco-dev/mailx-go`), `sdk/php` (Composer package `mailx/sdk`), and `sdk/ruby` (gem `mailx-sdk`) — all separate from the main Go module, zero coupling to `internal/`. Thin clients: generic request core (auth header, JSON, retry on 429/5xx honoring `Retry-After`), typed method per OpenAPI resource.
- Go SDK specifics: functional options (`WithBaseURL`, `WithHTTPClient`, `WithMaxRetries`), `context.Context` first-param on every method, `*APIError` on failure. Same fully-typed/loose-JSON split as Node/Python (`SendEmail`/`SendBatch`/`GetEmail`/`ListEmails` typed; rest return `mailx.JSON`).
- PHP/Ruby specifics: every method takes/returns a plain associative array (PHP) or hash (Ruby) mirroring OpenAPI field names — no hand-typed request/response classes for any resource, including email send (unlike Node/Python/Go's core-typed methods), since PHP/Ruby callers get less value from static structs. PHP's `Client` takes an injectable `Transport` (default `CurlTransport`); Ruby's `Client` takes an injectable `http_client` callable. Both used for test isolation, not runtime configuration.
- Release automation: `.github/workflows/sdk-release.yml` tars every `sdk/<lang>` dir and publishes a GitHub Release on each push to `main`, explicitly labeled "under active development" — no package-registry publishing (npm/PyPI/pkg.go.dev/Packagist/RubyGems) yet.
- Core send/batch/get/list email methods are fully typed against `internal/api`'s `SendEmailRequest`/`Email`/`BatchSendRequest`/`BatchSendResponse`; every other resource has a typed signature with a loosely-typed body/result (see each SDK's README for the exact-shape reference: `GET /openapi.json`).
- React Email: no SDK code — `@react-email/render`'s output is already the `html`/`text` shape `sendEmail` accepts (documented pattern only).
- Both SDKs have unit tests (fake HTTP layer: request shape, auth header, 429-retry-then-succeed, error mapping) and a gated contract test (`MAILX_SDK_TEST_BASE_URL`/`_API_KEY`) that runs against a real server when configured, skips cleanly otherwise.
- Go server side confirmed untouched (`git status` outside `sdk/` was empty before commit).
