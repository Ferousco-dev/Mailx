# MailX Milestone History (v0.1 -> v0.26)

Recovered 2026-09-21 from Git history (50 commits, `1218cf8`..`481da4a`) and the code at HEAD `481da4a`.
Method: commit diffs, package doc comments, migrations, and in-code `vX.Y` labels. No git tags exist.

**Evidence grades.** `LABELED` = the repo itself names the version (commit subject or code comment).
`INFERRED` = mapped by commit order/content; the version number is not written in the repo.
`UNAVAILABLE` = history cannot establish it. Nothing below is taken from memory or old prompts.

**Boundary caveats.** Several milestones landed in one commit, and the four review-fix commits
after v0.20 carry no version label. Milestone-to-commit mapping for v0.1-v0.6 is INFERRED (six
feature/fix commits, in order). The repository never recorded per-milestone completion dates beyond
commit dates (all v0.1-v0.15 work is dated 2026-09-13..15).

- v0.38 Advanced Analytics: **COMPLETE** (validated 2026-09-22). Migration 000022 (adds `analytics:read` API-key scope only — no new table). Read-only tenant-facing analytics derived entirely from the EXISTING `events` table (queued/delivered/deferred/bounced/failed/suppressed/complained, already indexed via `idx_events_tenant_occurred`) and `suppressions` (current-state count) — no OLAP infrastructure, no aggregate/derived table, no cache. Three endpoints: `GET /v1/analytics/overview`, `GET /v1/analytics/timeseries`, `GET /v1/analytics/broadcasts/{id}`. Metric vocabulary defined precisely in `internal/database/analytics.go`'s package doc: "delivered" is SMTP acceptance only, never inbox placement; an earlier accepted fact is never erased by a later async bounce/complaint (both counted); Broadcast analytics uses the DURABLE `broadcast_recipients` snapshot, never live Audience membership (proven via a mutation-caught test). Time range is `[from,to)` half-open, RFC 3339, capped at 90 days; timeseries buckets ("hour"|"day", UTC-truncated) are sparse (empty buckets omitted, not zero-filled) and capped at 744 buckets, rejected analytically BEFORE query execution (not just after). EXPLAIN evidence at 50k synthetic events / 90-day spread, 1-day query window: index scan via `idx_events_tenant_occurred`, 17 buffer hits, <0.15ms (both overview and timeseries). Open/click tracking deliberately NOT implemented (see architecture.md's boundary note). Analytics failure cannot block sending (read-only queries, no coupling to the accept/dispatch/worker path). Does NOT close RSK-035 (feedback-ingestion PARSER/correlation operator metrics — a different, still-open concern from this milestone's tenant-facing sending analytics).

See architecture.md's "v0.39 Sending Pools / Routing" section for the full design (three-layer model, decisions DEC-157..DEC-161, disabled-member kill-switch semantics). Operator-CLI-only (`create-sending-pool`, `create-sending-pool-member`, `enable/disable-sending-pool[-member]`, `assign-domain-pool`) — no tenant-facing REST API added. `internal/routing` package (pure `SelectMember` stable-hash + `Router` process-local dispatcher) is new; `internal/smtp.ClientConfig.SourceIP` (real `net.Dialer.LocalAddr` binding, not just a DB column) was the prerequisite groundwork. Zero pools configured preserves pre-v0.39 behavior exactly (proven by dedicated tests). Fixed two real bugs the DB-layer test suite caught: (1) `pgx` cannot scan a PostgreSQL `inet` column directly into `*string` — every `source_ip`/`effective_source_ip` read must use `host(...)` in the SELECT; (2) this package's migration-upgrade regression tests (`TestWebhookMigrationUpgradesDurabilityPrerequisite`, `TestDeliveryOutcomeMigrationUpgradesV021Data`, `TestSuppressionMigrationUpgradesAndDowngradesExistingData`) enforce that `InsertMessage`/`PersistDeliveryOutcome` must keep working against a schema missing the 1-2 most recent migrations (a standing rolling-deploy-safety invariant in this codebase) — fixed by making the v0.39 columns' INSERT clauses conditional on actually having a non-nil/non-empty value, never touched on the legacy no-pool path. - v0.41 Batch Sending: **PLANNED, NOT STARTED.** `POST /v1/emails/batch` — N distinct emails (different recipients/content each) accepted in one API call, unlike v0.36 Broadcasts (one template to one audience). Reuses the existing single-send acceptance path (`InsertMessage`, idempotency, abuse controls) per item, bounded batch size, partial-failure reporting (which items were accepted vs rejected) rather than all-or-nothing.
- v0.42 SMTP Submission: **PLANNED, NOT STARTED.** An authenticated SMTP submission endpoint (port 587/465, SMTP AUTH) so customers can send through MailX via SMTP client libraries instead of only the REST API — distinct from v0.25's outbound relay-THROUGH config (that's MailX relaying OUT through a smart host; this is customers relaying IN through MailX). Reuses the existing send/accept/abuse-control pipeline once authenticated; the new surface is the SMTP AUTH listener and translating a submitted message into the same durable acceptance path POST /v1/emails uses.
- v0.43 Open & Link Tracking: **PLANNED, NOT STARTED.** Tracking pixel injection (open tracking) and link rewriting through a redirect endpoint (click tracking), opt-in per send/template. New durable event types, a redirect/pixel HTTP surface, and privacy-conscious defaults (documented opt-out, no tracking on unsubscribe/compliance links).
- v0.44 Official SDKs: **PLANNED, NOT STARTED.** Thin client libraries (Node/TypeScript and Python first) wrapping the REST API — auth, retries, typed request/response shapes. Includes React Email template-authoring support (compiling JSX templates to the subject/html/text shape POST /v1/emails already accepts) as part of the Node SDK's template story, not a server-side feature.
- v0.45 Deliverability Insights: **PLANNED, NOT STARTED.** An analytics/reporting layer over existing durable events (delivered/bounced/complained/opened/clicked once v0.43 exists) — aggregate rates, trends, per-domain breakdowns. Read-only over existing data; no new event types beyond what v0.32/v0.43 already produce.
- v0.46 Data Retention & GDPR Tooling: **PLANNED, NOT STARTED.** Configurable retention windows (messages/events currently kept indefinitely), a scheduled purge job, and data export/delete-on-request tooling for GDPR-style subject access/erasure requests. Needs an explicit retention-policy design (per-tenant? per-plan?) before implementation — do not start without one.
- v0.47 Dashboard Backend (Human Accounts -> Organizations -> Dashboard): **PLANNED, NOT STARTED, CORRECTED SCOPE 2026-09-22.** Full client-server backend for the future web dashboard, built in three internally-ordered layers (each is a real dependency of the next, not just a suggested sequence): (1) Human Accounts — MailX is currently API-key-only with no human accounts at all; needs session model, login, social login, SSO, MFA. (2) Organizations — team/org structure sitting above today's flat per-tenant model, membership, roles/RBAC. (3) Dashboard backend proper — the server-side API surface a future dashboard FRONTEND will call (distinct from the tenant-facing `/v1` API), serving human-authenticated sessions rather than API keys, exposing v0.38's analytics and other resources for human consumption. Still backend/core only — no frontend, no React/Next.js, matches v0.38's "no frontend" boundary. Substantial scope; a real design pass (session model, org/team data model, RBAC vs today's flat tenant model, how human sessions coexist with API-key auth) is required before implementation, not assumed from a pricing-page feature list.
- v0.48 Stress Test (pre-deployment): **PLANNED, NOT STARTED.** The longest milestone in the roadmap. A comprehensive load/stress test of every MailX feature (send with attachments, templates, contacts, audiences, broadcasts, scheduled sending, analytics, webhooks) run locally in a virtual environment before any real deployment, using Mailpit as the local mail-capture target. Traffic profile: measured from low traffic up to heavy traffic, with heavy-traffic ceilings deliberately calibrated against the actual target deployment constraint — an AWS instance around the $7/month tier (plus a ~$200 AWS free-credit window usable only once real deployment begins, not during local testing) — so results are used to find MailX's real operating limits on that hardware class, not an arbitrary synthetic number. Must produce concrete evidence (throughput, latency, resource usage, failure modes at saturation, backpressure/abuse-control behavior under load) before v1/production readiness is declared. Needs its own design pass before implementation: exact traffic profiles, measurement methodology, and pass/fail criteria are not yet defined.

Deliberately excluded from the roadmap (infra/org concerns, not MailX code): SOC 2 Type II certification, penetration testing, DDoS protection, automated backups. General inbound email remains excluded pre-v1 (CR-015).
