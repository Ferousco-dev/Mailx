Recovered 2026-09-21 from Git history (50 commits, `1218cf8`..`481da4a`) and the code at HEAD `481da4a`.
Method: commit diffs, package doc comments, migrations, and in-code `vX.Y` labels. No git tags exist.

**Evidence grades.** `LABELED` = the repo itself names the version (commit subject or code comment).
`INFERRED` = mapped by commit order/content; the version number is not written in the repo.
`UNAVAILABLE` = history cannot establish it. Nothing below is taken from memory or old prompts.

after v0.20 carry no version label. Milestone-to-commit mapping for v0.1-v0.6 is INFERRED (six
feature/fix commits, in order). The repository never recorded per-milestone completion dates beyond

- v0.38 Advanced Analytics: **COMPLETE** (validated 2026-09-22). Migration 000022 (adds `analytics:read` API-key scope only — no new table). Read-only tenant-facing analytics derived entirely from the EXISTING `events` table (queued/delivered/deferred/bounced/failed/suppressed/complained, already indexed via `idx_events_tenant_occurred`) and `suppressions` (current-state count) — no OLAP infrastructure, no aggregate/derived table, no cache. Three endpoints: `GET /v1/analytics/overview`, `GET /v1/analytics/timeseries`, `GET /v1/analytics/broadcasts/{id}`. Metric vocabulary defined precisely in `internal/database/analytics.go`'s package doc: "delivered" is SMTP acceptance only, never inbox placement; an earlier accepted fact is never erased by a later async bounce/complaint (both counted); Broadcast analytics uses the DURABLE `broadcast_recipients` snapshot, never live Audience membership (proven via a mutation-caught test). Time range is `[from,to)` half-open, RFC 3339, capped at 90 days; timeseries buckets ("hour"|"day", UTC-truncated) are sparse (empty buckets omitted, not zero-filled) and capped at 744 buckets, rejected analytically BEFORE query execution (not just after). EXPLAIN evidence at 50k synthetic events / 90-day spread, 1-day query window: index scan via `idx_events_tenant_occurred`, 17 buffer hits, <0.15ms (both overview and timeseries). Open/click tracking deliberately NOT implemented (see architecture.md's boundary note). Analytics failure cannot block sending (read-only queries, no coupling to the accept/dispatch/worker path). Does NOT close RSK-035 (feedback-ingestion PARSER/correlation operator metrics — a different, still-open concern from this milestone's tenant-facing sending analytics).

- v0.41 Batch Sending: **COMPLETE** (validated 2026-09-22). `POST /v1/emails/batch`, up to 100 items, `emails:send` scope. No schema/migration — pure API-layer reuse of the single-send acceptance path: the entire `handleSend` body (template render, build, DKIM/domain auth, suppression, idempotency, abuse controls, FileStore, InsertMessage) was extracted into a shared `emailHandler.acceptOne`, called once per batch item. Independent per item: its own transaction, its own `admitSend` abuse-control check (a batch cannot buy more throughput than N individual sends), partial-failure reporting (`{data:[{index,email?,error?}], accepted, rejected}`, never all-or-nothing). Idempotency is per-item (`idempotency_key` field), not a batch-level header. Request-rate-limit cost scales with batch size and a batch-wide processing deadline prevents silently-dropped items on a slow idempotency poll (PR #19 review fixes, DEC-179/180). See architecture.md's "Batch Sending" section and DEC-175..180. The pre-existing single-send test suite (109 tests) passed unchanged after the refactor, confirming zero behavioral regression.
