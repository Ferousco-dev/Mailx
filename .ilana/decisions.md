# Decisions

- DEC-001: Rigour 3 because MailX is production-oriented email infrastructure.
- DEC-002: Potential harm includes privacy exposure, false delivery diagnosis, credential leakage, and false health signals.
- DEC-003: Treat addresses, message content, API keys, webhook secrets, and infrastructure credentials as sensitive.
- DEC-004: Use a hybrid process: gated requirements/security verification with incremental Go construction.
- DEC-005: No fixed deadline is assumed; correctness and privacy outrank speed.
- DEC-006: The user is owner and approver; automated regression evidence compensates for a single-person implementation context.
- DEC-007: Success requires end-to-end correlation, low-cardinality metrics, safe health signals, privacy tests, and all validation gates passing.

## Recovered architectural decisions (2026-09-21 historical recovery; source: Git + code, see `milestones.md` / `architecture.md`)

Process decisions above (DEC-001..DEC-007) belong to the v0.23 FLEET run and stay current for v0.23.

- DEC-008 [v0.1-v0.5]: SMTP is implemented at protocol level (raw TCP, own state machine and reply handling) rather than via a library; the project's stated purpose is to understand and own the protocol. Evidence: `09cec8f` -> `internal/smtp`, README.
- DEC-009 [v0.3]: `mail.Envelope` (MAIL FROM/RCPT TO) is separate from `mail.Message` (headers/body) because delivery uses envelope recipients; headers never control routing (hidden Bcc). Evidence: `internal/mail/model.go`.
- DEC-010 [v0.5]: MailX assigns its own message ID; the `Message-ID` header is untrusted metadata. Raw `.eml` is stored byte-exact plus derived metadata; attachments are metadata-only on load. Evidence: `internal/storage/store.go`.
- DEC-011 [v0.6]: Transport limits are finite by default (zero value selects a finite default, never "unlimited" for size). Evidence: `internal/smtp/config.go`.
- DEC-012 [v0.7]: `Accepted` means 2xx to the DATA terminator; later QUIT failure is recorded, never reverses acceptance (RFC 5321 4.1.1.10). Evidence: `smtp/client.go`, `transfer.go`, `delivery.go`.
- DEC-013 [v0.9]: DNS package only discovers; Null MX (RFC 7505) is terminal and never falls back to implicit MX; NXDOMAIN and temporary failure are distinct; ASCII-only domains until IDNA is designed. Evidence: `internal/dns/resolver.go`.
- DEC-014 [v0.10]: MX fallback only for pre-session failures; a remote answer after session engagement is authoritative to avoid duplicate work/odd DSNs. Evidence: `delivery/policy.go`.
- DEC-015 [v0.11]: Retry defaults fail safe (zero Decision = TerminalFailure); Coordinator performs exactly one operation and never waits; caller owns timing and State. Evidence: `retry/`.
- DEC-016 [v0.12]: DSNs claim only what MailX can truthfully know (omit unknown RFC 3464 fields; unconfirmed sibling recipients get a generic diagnostic); generation is separate from sending. Evidence: `bounce/`.
- DEC-017 [v0.13/v0.16]: Queue is at-least-once by design; nothing can make remote SMTP and Ack atomic. Redis holds scheduling and claim ownership only. Lua scripts make each transition atomic; polling chosen over blocking primitives. Evidence: `queue/queue.go`, `redis.go`.
- DEC-018 [v0.14]: Fixed-size worker pool, no goroutine-per-job; worker depends on narrow interfaces (Loader, Coordinator, OutcomeStore). Evidence: `worker/worker.go`.
- DEC-019 [v0.15]: PostgreSQL is durable truth; tenant_id on every table from day one; crypto-random TEXT IDs; raw MIME stays in FileStore; per-operation `delivery_attempts` with MX detail as JSONB; indexes justified by real queries + EXPLAIN tests. Evidence: migration 000001.
- DEC-020 [v0.17]: Deterministic schema setup via a one-shot `migrate` service; Redis AOF; loopback-only ports. Evidence: `compose.yaml`.
- DEC-021 [v0.18]: Transactional outbox closes the commit-then-crash-before-enqueue gap; HTTP 202 = durably accepted. Dispatcher relies on duplicate-safe Enqueue plus guarded `MarkOutboxDispatched`, no new lock primitive. Evidence: migration 000004, `dispatch/`.
- DEC-022 [v0.18]: stdlib `net/http` (no framework); public API schemas decoupled from DB/worker structs; hand-written OpenAPI with drift test; mixed-domain sends rejected before acceptance because the engine delivers per domain. Evidence: `internal/api`.
- DEC-023 [v0.19]: API key = `mx_<key_id>_<secret>`, HMAC-SHA256 verifier (+pepper), no password hashing (256-bit random secret); rotation via `expires_at` grace; identical generic 401; scopes enforced in Go and DB CHECK; no public key-creation endpoint; rows never deleted. Evidence: `internal/auth`, migration 000006.
- DEC-024 [v0.20]: Idempotency arbiter is PostgreSQL only; scoped to tenant; fingerprint over validated request; completion in the same tx as the message insert; stale-claim reclaim with fingerprint-guarded completion; replay reflects current state. Evidence: `idempotency`, migration 000007, `8ba5264`..`389c31d`.
- DEC-025 [v0.21]: Domain ownership by DNS TXT proof with strict normalization; pending claims may overlap across tenants, verified ownership is unique; verification does not imply SPF/DKIM/DMARC. Evidence: `internal/domain`, migration 000009.
- DEC-026 [57ee1d0]: Delivery outcome (attempt + status + event) persists in one transaction before queue finalization; worker consults durable state before SMTP; queue `Renew` protects live workers during DB outages; retry state rebuilt from PostgreSQL. Replaces best-effort status reporting. Evidence: `worker/processor.go`, `database/outcomes.go`, migration 000010.
- DEC-027 [v0.22]: `events` is the single event truth; webhooks are derived fan-out (separate tables, atomic fan-out, per-subscription delivery rows). Public event names are a stable mapping decoupled from internal names; `delivery_attempted` stays internal. Evidence: `database/events.go`, `webhook_fanout.go`.
- DEC-028 [v0.22]: Webhooks are at-least-once with stable event ID; consumers deduplicate; no exactly-once claim. Evidence: OpenAPI text, `UNIQUE(subscription_id,event_id)`.
- DEC-029 [v0.22]: Signing secrets need recoverable storage, so AES-256-GCM with a master key and tenant-ID AAD instead of one-way hashing; HMAC-SHA256 `v1` signature over `timestamp.body`. Evidence: `webhook/secret.go`, `signing.go`.
- DEC-030 [v0.22]: SSRF defence is enforced at dial time as well as at creation to defeat DNS rebinding; no proxies, no redirects. Evidence: `webhook/policy.go`, `client.go`.
- DEC-031 [v0.22]: Webhook delivery uses PostgreSQL leases with fencing tokens and `SKIP LOCKED`, not Redis, so notification work is independent of the email queue. Evidence: `database/webhook_deliveries.go`.
- DEC-032 [recovery]: `.ilana/` had never been committed and stopped being maintained after the initial milestones; from 2026-09-21 Ilana updates are mandatory per task (`CLAUDE.md`).
- DEC-033 [v0.23]: Observability is a leaf package; components get optional logger/metrics (nil-safe, panic-guarded) so behavior is unchanged when absent. Prometheus official client with a private pedantic registry; label values allowlisted else `other`.
- DEC-034 [v0.23]: Operator listener is separate from the developer API (`MAILX_OBSERVABILITY_ADDR`, default `:9090`, empty disables); developer `/health/ready` shares the bounded readiness checker and no longer echoes raw errors.
- DEC-035 [v0.23]: Queue depth and ping are concrete `RedisQueue` methods (interface unchanged); depth and its error counter come from one collector so a scrape is self-consistent.
- DEC-036 [v0.23]: A worker survives transient queue-claim failures (DEF-004) so dependency outages degrade readiness instead of killing the process.
- DEC-037 [v0.24]: Outbound STARTTLS is a small explicit state machine in `client_tls.go`; `raw` vs `conn` split keeps deadlines race-free across the upgrade; capabilities are nil'd when the handshake starts and only ever set from the latest EHLO.
- DEC-038 [v0.24]: Two policies only (`opportunistic` default, `required`). Default is opportunistic because RFC 3207 forbids public servers from requiring STARTTLS; it never downgrades after attempting TLS (stricter than MTAs that retry plaintext after a failed handshake).
- DEC-039 [v0.24]: Certificate verification is always on (no insecure option). Opportunistic therefore verifies too; peers with self-signed/mismatched certs are deferred until fixed or trusted via `MAILX_SMTP_TLS_CA_FILE` (extra roots added to the system pool). An unverified-encryption mode was deliberately not built.
- DEC-040 [v0.24]: All TLS-stage failures are temporary (statements about the connection, not the recipient) and the delivery engine tries the next MX for them (before MAIL FROM, same policy), reusing the existing retry model.
- DEC-041 [v0.24]: Inbound STARTTLS is deferred (needs certificate provisioning/reload); the inbound EHLO must not advertise it.
- DEC-042 [v0.24]: Test infrastructure lives in `internal/smtp/smtptest` (ephemeral in-memory CA + scriptable fake MX) so smtp, delivery-style and worker pipeline tests share one deterministic TLS server.
- DEC-043 [v0.25]: Trusted relay is an explicit `delivery.Config.Relay`; relay mode replaces MX routing entirely and never falls back to direct delivery, so an operator's "deliver through this relay" intent cannot be silently bypassed.
- DEC-044 [v0.25]: Credentials exist only inside `Config.Relay` and per-request `DeliveryRequest.Auth`; the SMTP client holds none. This makes "credentials never reach a DNS-discovered MX" structural rather than a runtime check.
- DEC-045 [v0.25]: Mechanisms PLAIN (preferred) and LOGIN only, only over verified TLS; credentials force TLS-required regardless of policy. OAuth/XOAUTH2, SCRAM, CRAM-MD5 deferred or rejected (see design doc).
- DEC-046 [v0.25]: Every auth-stage failure is a temporary attempt at the engine (existing backoff, never another MX): authentication describes relay configuration, not the message, so bouncing senders permanently for an operator error was rejected.
- DEC-047 [v0.25]: Remote AUTH reply text is discarded (code and enhanced status only) and error text is a fixed category, because servers may echo credentials.
- DEC-048 [v0.26]: rsa-sha256 with 2048-bit keys only, relaxed/relaxed; Ed25519 deferred (uneven receiver support, would need dual signing). Own canonicalization, standard-library crypto, verified by an independent implementation in tests.
- DEC-049 [v0.26]: sign at API acceptance, so stored = queued = transmitted bytes and signing failures reject the request instead of failing after acceptance; retries resend the stored (already signed) bytes.
- DEC-050 [v0.26]: a domain with an active key ALWAYS signs and any key failure refuses the send (no unsigned fallback); a domain without an active key sends unsigned (DKIM not set up). Pending keys never sign.
- DEC-051 [v0.26]: verified-From is an exact canonical-name match against the tenant's verified domains (v0.21 root/subdomain independence preserved), enforced before durable acceptance and re-checked in the insert transaction.
- DEC-052 [v0.26]: private keys are AES-GCM encrypted with a dedicated `MAILX_DKIM_MASTER_KEY` that must differ from the webhook key; `internal/secretbox` extracted so both use one reviewed primitive; ciphertext bound to tenant/domain/selector via AAD; retired keys lose their ciphertext; domain deletion deletes keys.
- DEC-053 [v0.26]: lifecycle is pending -> active -> retired with partial unique indexes and a per-domain row lock for concurrency safety; rotation = create + publish + verify, and the old key signs until activation.
- DEC-054 [v0.27]: sending is NOT blocked when SPF is missing, wrong or unverifiable. Authorization = verified domain ownership, signing = active DKIM key, SPF = readiness information; a stricter "require full authentication" policy is a later, explicit production decision. Local dev must not need public DNS.
- DEC-055 [v0.27]: SPF identity is the MAIL FROM domain (= From-address domain in MailX). HELO is `mailx.local` and not SPF-capable; changing it is v0.29 deliverability work, only documented here.
- DEC-056 [v0.27]: sending infrastructure is operator-declared (`MAILX_SENDING_IPS` public-only, or `MAILX_SPF_RELAY_INCLUDE`), mutually exclusive with the routing mode; no egress auto-discovery; in relay mode MailX invents no authorization for infrastructure it does not control.
- DEC-057 [v0.27]: verify only the literal subset (ip4/ip6 or named include); never follow include/a/mx/exists/ptr/redirect (unbounded DNS work, RFC 7208 4.6.4 limit); say so via `unevaluated_mechanisms` rather than claim full evaluation. One DNS query per verification.
- DEC-058 [v0.27]: exactly one SPF record per domain: existing records are extended (mechanisms inserted at the front so they match first), multiple records are a `conflict` with no generated value, oversized merges are refused.
- DEC-059 [v0.27]: SPF state is not persisted (DNS is truth; no stale copies); GET gives guidance without DNS, POST verify does one lookup, requires a verified owned domain (no DNS probing of arbitrary names) and stores nothing. Distinct statuses replace any single verified boolean so v0.28 DMARC can use them.
- DEC-060 [v0.28]: RFC 9989 is the DMARC standard used (RFC 7489 is obsolete); differences from 7489 are followed and documented.
- DEC-061 [v0.28, SUPERSEDED by DEC-066]: organizational domain for alignment = ICANN PSL registrable domain through `domain.Normalize` (offline, deterministic), not the RFC 9989 tree walk; never suffix matching. Policy discovery walks only from the domain to its organizational domain (max 8 queries).
- DEC-062 [v0.28]: recommended initial policy is `p=none` with no rua/ruf; existing policies are never rewritten or duplicated; enforcement progression is the owner's decision (MailX has no report intake to prove alignment holds).
- DEC-063 [v0.28]: readiness is sender-side only and separate from any receiver result (`receiver_result: not_observed`); distinct dns/path/readiness states replace a single boolean; relay-mode SPF alignment is `unknown`, never faked.
- DEC-064 [v0.28]: missing or invalid DMARC never blocks sending (authorization = ownership, signing = DKIM, SPF/DMARC = readiness); DMARC cannot grant From authorization.
- DEC-065 [v0.28]: no persistence for DMARC (DNS is truth); DKIM/SPF are consumed as facts through interfaces so `dmarc` imports neither and cannot alter them.
- DEC-066 [v0.28 correction]: the RFC 9989 DNS Tree Walk (sections 4.10, 4.10.1, 4.10.2) is the sole authority for the DMARC Organizational Domain and for policy discovery, as ONE walk so both come from the same interpretation; `psd=n`/`psd=y` are implemented; the PSL and suffix matching are forbidden in `internal/dmarc` production code (tested). Supersedes DEC-061.
- DEC-067 [v0.28 correction]: multiple DMARC records at a name are discarded and the walk continues (RFC 9989 4.10 step 2), but MailX reports `conflict` when that hides the domain's own record or leaves no governing policy, because receivers silently fall back and the owner must fix it.
- DEC-068 [v0.28 correction]: any DNS error during the walk fails safe (`temporary_error`, readiness `unknown`); no parent policy is substituted and no boundary guessed; relaxed alignment that could not obtain a boundary is `unknown`, never "not aligned" or "ready". Strict and identical-domain alignment never need DNS.
- DEC-069 [deployment, 2026-09-21, user decision]: the first production/deployment target is an AWS Lightsail Linux instance on the $7/month plan (fixed static IP included). Sources for the plan: user choice; AWS promo of 3 free months on select $5/$7/$12 plans and student credits (AWS Free Tier, AWS Educate) were reported by web search, not verified against AWS. The $7 bundle is 'Micro-1GB Linux with public IPv4': 2 vCPU, 1 GB RAM, 40 GB SSD, 2 TB transfer, per the user's own Lightsail console listing (not independently verified by us). The $5 'Micro-1GB Linux IPv6-only' plan has the same hardware but no public IPv4 and is unsuitable for MailX (mail reputation, SPF/PTR, port 25 request and tooling all depend on IPv4). Measured stack memory on the dev machine: MailX ~8.5 MiB, PostgreSQL ~248 MiB, Redis ~7 MiB (~265 MiB). Whether PostgreSQL stays on the same host or moves to a managed service (Aiven free plan: 1 CPU, 1 GB RAM, 1 GB storage, max_connections 20, no static IP, single node) is decided in DEC-070.
- DEC-070 [deployment, 2026-09-21, user decision]: on the AWS Lightsail $7 host (DEC-069) run MailX, PostgreSQL and Redis together on the one server (docker compose). Reasons: measured stack ~265 MiB fits a 1 GB host after tuning PostgreSQL memory and adding a small swap file; one thing to operate; no network hop per database call; no dependency on a free managed plan that could change; hosted TLS/password Redis is unsupported anyway (architecture limitation 19). Backups are mandatory from day one: a nightly `pg_dump` copied off the server, because API keys, domains and encrypted DKIM keys live only in PostgreSQL (RSK-025; the raw MIME store on local disk is a separate backup concern). Managed PostgreSQL (for example Aiven) is a LATER option if the box is outgrown or managed backups are wanted; it is a `DATABASE_URL` change (`sslmode=require`), and latency from Lightsail must be measured before switching. Not yet implemented: no deployment, tuning or backup script exists in the repository.
- DEC-071 [v0.29]: the SMTP infrastructure hostname (`MAILX_SMTP_HOSTNAME`) is an operator concept separate from tenant domains: it is configured, never derived from a tenant domain, and does not align with any tenant's DMARC domain; tenants never own PTR.
- DEC-072 [v0.29]: identity modes are static and explicit: sending IPs declared => hostname required (startup fails); hostname present => strict validation; neither => local `mailx.local`; relay without hostname => local with a warning. DNS is never consulted at startup or in health.
- DEC-073 [v0.29]: generated Message-IDs use the infrastructure hostname (RFC 5322 3.6.4), built once before DKIM signing; no user-supplied Message-ID exists to preserve; the signed stored bytes are never mutated.
- DEC-074 [v0.29]: readiness is per-IP FCrDNS with membership semantics; multiple PTR names pass with a warning only when ours is among them; any definite failure makes the set not ready, uncertainty makes it unknown, and a healthy IP never hides a broken one; nothing is persisted.
- DEC-075 [v0.29]: infrastructure diagnostics are an operator CLI, not an API or health check (PTR is the operator's; caller-supplied lookups would be an SSRF-style probe; health must not depend on public DNS).
- DEC-076 [v0.29]: HELO SPF is advisory guidance (RFC 7208 2.3 recommends verifiers check it; it is the only identity for null-reverse-path mail) and never gates `ready`; PTR is never SPF authorization.
- DEC-077 [deployment, 2026-09-21, user decision]: PostgreSQL memory tuning ships as an OPT-IN Compose override (`compose.low-memory.yaml`, documented in `docs/low-memory-deployment.md`), NOT as the global defaults. Evidence (measured here on `postgres:16`, same `pgbench -i -s 5` + `-c 5 -j 2 -T 8` load on fresh instances): 122.2 MiB with stock settings vs 50.8 MiB tuned (`shared_buffers=32MB`, `max_connections=20`, `work_mem=2MB`, `maintenance_work_mem=16MB`, `wal_buffers=1MB`, `max_wal_size=256MB`, `effective_cache_size=128MB`, fewer autovacuum/background/parallel workers). The long-running dev database shows ~288 MiB from accumulated data and cache; Redis ~7 MiB and MailX ~8 MiB are already small. Reasoning: the default must keep local development and the test suite on stock settings; the profile targets ~1 GB hosts (the Lightsail $7 plan, DEC-069/070). Durability is preserved and pinned explicitly (`fsync`, `synchronous_commit`, `full_page_writes` on) because MailX persists outcomes before acknowledging jobs and accepts an email only after commit. 20 connections suffice (pool 10 + 3 reserved + migrate/CLI); the whole suite passed six times against a server with `max_connections=20`.
- DEC-078 [v0.30]: suppression is tenant-scoped policy (`UNIQUE (tenant_id, email)`), separate from delivery history; creating or deleting one never rewrites, retries or resurrects anything; cross-tenant access is 404.
- DEC-079 [v0.30]: ONE canonical key function (`suppression.Normalize`) for API, worker and store; ASCII only; the local part is lower-cased for the KEY ONLY (fail-safe direction for a deny list; RFC 5321 2.4 discourages case-sensitive local parts; transport still preserves case); dots and `+tag` are never folded; every accepted recipient must be keyable.
- DEC-080 [v0.30]: reasons manual|hard_bounce|complaint|unsubscribe and sources api|delivery|feedback are stored vocabulary (WHY vs HOW) but only manual/api and hard_bounce/delivery are produced; the API creates only `manual`, so callers cannot forge system-derived facts; complaint/unsubscribe/feedback wait for v0.32 and a subscription product.
- DEC-081 [v0.30]: auto-suppress only a recipient-specific permanent mailbox rejection: permanent RCPT TO with 5.1.1 or 5.1.6 (RFC 3463); never temporary failures, sender/policy/authentication/content failures, domain-level codes, mailbox-full/disabled, or a bare 550. Suppression commits in the same transaction as the outcome.
- DEC-082 [v0.30]: enforce suppression at BOTH acceptance (fast feedback; all suppressed => 422 nothing stored, key not consumed; partial accepted) and delivery (authoritative, per attempt including retries, before any transport; recipient-level: suppressed recipients are removed from the envelope, all suppressed => zero SMTP).
- DEC-083 [v0.30]: consistency boundary: the worker's check is the guarantee; a suppression created afterwards does not revoke an in-flight attempt; no DB lock across SMTP I/O; accepted delivery history is immutable.
- DEC-084 [v0.30]: fail safe: unknown suppression state defers the job (15 s, no attempt, no counter movement) instead of sending or failing the message.
- DEC-085 [v0.30]: new terminal message status and recipient status `suppressed` (not failed/bounced) and one lifecycle event `suppressed`/`email.suppressed` (counts only, once per message); list mutations are not events.
- DEC-086 [v0.30]: unsuppression is a hard delete (simple uniqueness and a trivial safety-critical query; cost: no removal audit trail); no Redis cache, PostgreSQL only, measured ~0.36 ms per attempt.
- DEC-087 [v0.31]: rate limiting is GCRA (a token bucket kept as one timestamp) in a single atomic Redis Lua script with Redis `TIME` as the only clock: O(1) state, exact Retry-After, multi-bucket all-or-nothing so a refused request charges nothing, one round trip per decision; rejected: fixed windows (burst at boundaries), sliding-window logs (memory per request), per-process limiters (wrong with several processes).
- DEC-088 [v0.31]: the tenant is the primary boundary and API keys can never raise a limit: the request tenant bucket is charged by every key, a per-key guard (<= tenant limit) only stops one key using the whole allowance.
- DEC-089 [v0.31]: charge order and idempotency: replays and 409s are free; after the claim is owned check tenant queue cap, then global backlog, THEN charge recipient tokens (least side effect first); recipient cost = deliverable (unsuppressed) recipients; a refusal deletes the claim it owns so the same key retries after Retry-After. Trade-off: tokens are not refunded if PostgreSQL fails after the charge.
- DEC-090 [v0.31]: failure policy: sends and other mutating requests FAIL CLOSED when the limiter is unavailable (503 + Retry-After) because an outage must not mean unlimited sending (auth/readiness precedent); GETs fail open so a Redis blip is not a full outage; unknown permit state defers delivery without an attempt. Rejected: fail open everywhere (unmetered abuse during outages).
- DEC-091 [v0.31]: 429 means the tenant/key exceeded ITS limit; 503 means MailX is at capacity or cannot enforce limits; both carry Retry-After (whole seconds, exact for rate limits, fixed 30 s for capacity); OpenAPI adds them programmatically to every operation so the contract cannot drift.
- DEC-092 [v0.31]: fair dispatch by round robin across tenants (recursive loose index scan + LATERAL per-tenant slice + rank interleave) instead of global `available_at` order; drop `FOR UPDATE SKIP LOCKED` (no-op in an implicit transaction); migration 000014 replaces `idx_outbox_pending` with `idx_outbox_pending_tenant` because with both, the planner filtered 15,000 rows behind a large backlog (EXPLAIN evidence) and one index halves outbox write cost.
- DEC-093 [v0.31]: per-tenant and per-destination concurrency are lease permits (ZSET holder->expiry, prune on acquire, TTL crash recovery), taken after suppression and before any transport; refusal defers with jitter and records no attempt, so backpressure can never fail or bounce a message; release uses a fresh context.
- DEC-094 [v0.31]: retry storms are broken with deterministic bounded jitter (FNV of the scheduling instant, +/- N%, never above Max, never below 1 s), default 10%, configurable 0-50; it is not randomness a test cannot pin.
- DEC-095 [v0.31]: safety configuration is strict: an invalid value fails startup naming the variable (contrast lenient tuning knobs), cross-field rules are validated, `off` is the only opt-out and is logged loudly; abuse metrics use closed label sets (max 30 series) and never carry tenant/key/address/domain.
- DEC-096 [v0.32]: feedback lands at the RECIPIENT level (`recipients.feedback_status/feedback_at`), never rewriting `delivery_attempts`/`messages.status`; a multi-recipient message's coarse status is not collapsed to one recipient's later feedback.
- DEC-097 [v0.32]: correlation token = HMAC-SHA256(secret, messageID), truncated 128 bits, hex; ingestion route also accepts a bare message_id because the route itself requires an operator-only credential — VERP Return-Path (`bounce+<token>@bounce-domain`) was evaluated and deferred to avoid a MAIL FROM change and new DNS this milestone (RSK-036).
- DEC-098 [v0.32]: `EventBounced` (reserved since v0.18) is reused for feedback-driven bounces rather than adding a second bounce event type; `EventComplained`/`email.complained` is new.
- DEC-099 [v0.32]: idempotency key = UNIQUE(message_id, recipient_id, sha256(raw bytes)); the recipient-level state transition (not just the history row) additionally gates suppression/event emission, so a semantically-repeated but byte-different DSN never double-fires.
- DEC-100 [v0.32]: async suppression reuses the exact narrow enhanced-status set as v0.30's synchronous rule (5.1.1/5.1.6), factored into `suppression.hardBounceEnhancedStatuses`, so the two paths cannot diverge.
- DEC-101 [v0.33]: template rendering is a hand-written bounded `{{identifier}}` substitution, not text/template — avoids exposing an action language (if/range/pipelines) as an unintended attack surface; deterministic, single-pass, no recursive expansion.
- DEC-102 [v0.33]: HTML variable substitution is always `html.EscapeString`-ed; no raw/unescaped-HTML variable mode in v0.33 (conservative default, explicitly the only model).
- DEC-103 [v0.33]: template send is mutually exclusive with explicit subject/html/text (422 on conflict) — never a silent precedence choice.
- DEC-104 [v0.33]: idempotency fingerprint is computed on the ORIGINAL request (template_id+variables), not rendered output, so a template edit between an accepted send and a same-key retry cannot create a duplicate or change the replayed content — it replays the original durable message.
- DEC-105 [v0.33]: template name uniqueness is a DB constraint (`UNIQUE(tenant_id,name)`), not only application validation — same precedent as domain-name uniqueness.
- DEC-106 [v0.33]: template deletion is a hard delete with no versioning; already-sent messages are independent rows/files, unaffected by template edits or deletion.
- DEC-107 [v0.34]: contact identity normalization is a SEPARATE function from suppression.Normalize — domain folding shared, but local-part case is PRESERVED (not folded), because a contact identifies a real mailbox where merging case variants risks conflating two people, unlike a deny-list where over-blocking is the safe direction.
- DEC-108 [v0.34]: contacts and suppressions have zero FK/cascade relationship in either direction; contact deletion/recreation/update never touches suppression state, by construction (verified: separate tables, separate normalization, no trigger).
- DEC-109 [v0.34]: contact attributes are a bounded flat string map (JSONB storage, CHECK-enforced object shape + size), not arbitrary JSON — avoids nested/array/executable payloads without inventing a schema system.
- DEC-110 [v0.34]: sending never requires or auto-creates a contact; Contacts is additive, not a gate on `/v1/emails`.
- DEC-111 [v0.34]: no `contact.*` webhook events and no contact-specific metrics in v0.34 — neither has an identified consumer yet; recorded as a deliberate omission, not an oversight.
- DEC-112 [v0.35]: audience membership tenant integrity is enforced by composite FKs on `audience_members` (tenant_id + audience_id, tenant_id + contact_id), not application checks alone — a cross-tenant row is a schema-level impossibility, verified by mutation-removing the app-level check and confirming the isolation test still fails correctly.
- DEC-113 [v0.35]: `audience_members` cascades on EITHER side (audience delete or contact delete) removes ONLY join rows; contacts/audiences/suppressions are never cascade-deleted into each other.
- DEC-114 [v0.35]: adding an already-present member is idempotent (204, no error), matching suppression's create-if-absent precedent rather than 409 — a group-membership add is naturally repeatable, unlike a named-resource create.
- DEC-115 [v0.35]: membership pagination keys on the membership row's own created_at, not the contact's, for stable ordering independent of contact history.

- DEC-208 [v0.47 phase 1, made with the human operator before this session]: human auth is a separate code path from API-key auth (`internal/humanauth`, not folded into `internal/auth`) because the threat models differ: passwords are low-entropy/human-chosen (bcrypt, `golang.org/x/crypto/bcrypt`, already an indirect dependency promoted to direct), while API keys are high-entropy random secrets (HMAC-pepper, see `internal/auth/apikey.go`'s doc). Also pre-emptively applied DEC-226's fix for the SAME underlying bug the naive version of this split would have reintroduced: `SupersedeOtherEmailVerificationTokens` compares the full `(created_at, id)` tuple, not `id != keep`, so two concurrent successful resends can never mutually invalidate each other (whichever's UPDATE runs last), and `created_at` is set via `clock_timestamp()` at INSERT time rather than the column's `now()` default, since a transaction that waited on the `humans` row lock would otherwise capture an earlier timestamp than one that acquired the lock and committed first - the exact ordering-skew DEC-226 diagnosed for org invitations. Proven by a new `TestFailedResendDoesNotInvalidateTheWorkingVerificationLink` and by re-running the existing `TestConcurrentResendsLeaveExactlyOneValidToken` 15x (150 total race trials) with `-race`, all clean.
